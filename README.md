# requirement-quality

研究**需求的有效性**：什么样的需求描述拿去开发，会产出一个"能用但不符合预期"的结果。

## 定位

本仓库收集**无效 / 低质量需求样本**（合成样本 + 真实写法），每一条样本记录一个需求描述的典型缺陷，用于：

- 归纳"无效需求"的共性模式，形成**场景 × 缺陷矩阵**（见 [docs/METHODOLOGY.md](docs/METHODOLOGY.md) 与 `MATRIX.md`）；
- 为 AI 辅助需求澄清（clarifier）提供负样本与训练素材；
- 在写需求时对照自查，避免踩坑。

## 什么算"无效需求"

凡是**描述与预期产出之间存在信息缺口**的需求，都算无效。典型表现：

| 缺陷类型 | 示例 |
|---|---|
| 缺少校验规则 | 描述了"表单场景"，但没说字段是否必填、格式限制、长度上限 |
| 缺少边界条件 | 未定义空态、极值、并发、异常分支的行为 |
| 缺少验收标准 | 只有功能描述，没有"做到什么程度算完成" |
| 隐含假设 | "和现有系统保持一致"——但"现有"指哪个版本、哪个行为没说 |
| 主观形容词 | "界面要美观"、"性能要流畅"，无量化指标 |
| 流程断点 | 有正常流程，未覆盖失败/回退/撤销路径 |

## 调研方法论

整体思路（穷举场景 → AI 穷举无效写法 → 多解验证 → 矩阵承载 → 真实样本回测）详见 **[docs/METHODOLOGY.md](docs/METHODOLOGY.md)**。

## 目录结构

**规则与案例分层**——`rules/` 是机器消费的扫描规则库（skill / clarifier 只加载这里），`cases/` 是人读的案例证据库（含验证记录，兼作规则回归测试素材）：

```
rules/                       # 扫描规则库（skill 唯一消费源）
├── form.md                  # 数据录入组（S01–S04），规则 ID = R-<场景>-<标签>
└── ...
cases/                       # 案例证据库（人读 + 回归测试）
├── form/                    # 表单类
│   └── no-field-validation.md
├── flow/                    # 流程/交互类
└── ...
```

## 规则格式（rules/）

每条规则对应矩阵一个格子（场景 × 标签），内容无关：

- **命中条件**：正向特征 F / 反向特征 B，判定逻辑（布尔组合）；
- **说明**：缺口实质，与具体领域/字段无关；
- **误报注意**：什么情况不该命中却可能命中（如外部引用、分期承诺）；
- **漏报注意**：什么情况该命中却可能漏掉（如部分约束、约束词歧义）；
- **验证依据与关联案例**：链接 cases/ 证据。

## 案例格式（cases/）

每个案例文件 = **头部元信息 + 固定三段结构**：

```markdown
---
场景: S01-表单（新增/编辑）        # 对应 docs/SCENARIOS.md 场景 ID
缺陷标签: P1-不完整, P2-不可验证   # 对应 docs/DEFECTS.md，可多标签
规则: R-S01-P1                    # 对应 rules/ 规则 ID（规则本体只在 rules/，案例不内嵌）
验证: 多解实现验证通过（日期，N=x） # 或"待补"/"旁证——…"
---

# <一句话概括缺陷>

## 原始需求

> 原样摘录需求描述（脱敏后）。

## 缺陷分析

指出信息缺口在哪里、开发拿到后会怎么理解、可能产出什么偏差。
（AI 合成样本须附多解实现验证的分歧对比表）

## 应补充的内容

列出该需求要变得"有效"，至少需要补充哪些信息。
```

## 如何贡献

1. 新样本放入对应场景目录；没有合适的目录就新建一个类别（先修订 [docs/SCENARIOS.md](docs/SCENARIOS.md)）；
2. 文件名格式：`缺陷关键词.md`（kebab-case，不带日期前缀；创建日期记在样本头部 YAML）；
3. 原始需求一律脱敏，去掉公司/客户/系统真实名称。
