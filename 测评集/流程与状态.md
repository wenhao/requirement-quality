> 做一个请假审批流程，员工提交请假申请后走审批，审批通过后完成。

**预埋缺口**：`P7-流程断点`（驳回怎么办、撤回怎么办、审批人不在怎么办全未定义）；`P1-不完整`（审批级数、审批人规则）。

## S15 状态机

### CAND-017【已验证→沉淀规则】

（N=3：电商交易状态机派 / 中后台配置化派 / 小团队极简派）

> 订单有待支付、已支付、已发货、已完成、已取消这几个状态，用户下单后订单进入待支付状态。

**验证结论**：
- **冲突性假设（5 组）**：① 已支付订单能否取消、由谁触发：A 无取消入口（已支付逆向走独立售后）vs B 仅运营可取消（联动退款）vs C 用户自助一键取消+退款——同一笔已支付未发货订单，A 显示"申请退款"、B 须找客服、C 显示"取消订单"立即生效；② 取消合法来源状态集合：A 仅{待支付} vs B {待支付,已支付,已发货(可配置)} vs C {待支付,已支付}——已发货在途订单只有 B 用户会遇到"被取消+物流拦截+退款"；③ 系统自动流转（超时关单/自动收货）：A 固定强制 vs B 均为配置项 vs C 完全不做——一直不付款：A 半小时后自动取消，C 隔天仍能支付成功；④ 终态可操作性：A 自助售后起点 vs B 运营可强制取消已完成订单 vs C 彻底终态无售后——交易完成后想退货，A 自助、B 找客服、C 无入口；⑤ 非法流转处置：A 状态机强拦截 vs B 配置校验拦截 vs C 不拦截（后端裸 update）——取消与支付回调并发时 C 出现"已取消又变已支付"等用户可见脏状态。
- **伪缺陷剔除**：硬编码 vs 配置化的纯架构形态、状态字段命名与存储、ORM 选型、待支付→已支付由支付事件驱动（趋同）、幂等/并发锁实现深度、拦截机制的实现差异。
- **P1 实证成立**。已沉淀为 `场景/流程与状态/R-S15-P1.md`。

## S16 异常/回退/撤销

### CAND-018【已验证→沉淀规则】

（N=3：C 端交易风控优先 / SaaS 补偿事务派 / 小团队极简派）

> 做一个订单撤销功能，用户可以撤销自己的订单，撤销成功后订单关闭。

**验证结论**：
- **冲突性假设（7 组）**：① 允许撤销的状态边界：A 未支付+已支付未发货 vs B 全部未终态（含已发货/已完成冲销）vs C 仅未支付——刚付款未发货的订单 A/B 能撤、C 无入口；② 不可撤时入口反馈：A 置灰+原因 vs B 入口保留点击报错 vs C 隐藏入口；③ 被拒路径：A 风控可疑单转人工"审核中" vs B 明确原因+可重试 vs C 笼统 toast；④ 下游回滚同步性：A 退款异步回调+库存即时+券按有效期 vs B Saga 全链路最终一致 vs C 单事务同步全量——撤销后刷新资产页，C 瞬间恢复、A/B 分钟到天级延迟；⑤ 撤销中间态：A 仅已支付单有"退款中" vs B 一律"撤销中"独立撤销单 vs C 无中间态瞬时完成；⑥ 撤销后反悔：A 终态不可恢复 vs B 完成前可撤回申请、管理员可驳回 vs C 不可恢复——B 版本能撤回申请救回订单，A/C 订单直接没了；⑦ 二次确认强度：A 退款金额+到账时效+大额验证码 vs B 强制填撤销原因 vs C 原生 confirm 一键。
- **伪缺陷剔除**：终态命名、事务机制选型本身、接口风格与幂等键、审计落库方案、状态机实现方式、并发控制（乐观锁/CAS）、入口页面布局。
- **P7 实证成立**——原文仅定义"撤销成功→订单关闭"的 Happy Path，7 组互斥假设每组均导致用户可感知的流程分叉。已沉淀为 `场景/流程与状态/R-S16-P7.md`。

## S17 定时/触发任务

### CAND-019【已验证→沉淀规则】

（N=3：延迟消息一致性派 / 调度跑批对账派 / 小团队 cron 派）

> 订单超过 24 小时未支付自动取消。

**验证结论**：
- **冲突性假设（4 组）**：① 24 小时起算点：A 进入待支付时刻 vs B/C 下单时刻 created_at——拼团/预售等"下单后延迟才可支付"的订单，A 方案成团后仍有完整 24h，B/C 方案用户刚获支付资格订单就被取消；② 第 24 小时支付在途裁决：A 挂起取消以支付结果优先（付款成功订单保留）vs B/C 照常取消、事后对账/回调退款——临界点正在付款的用户，A 拿到订单，B/C 付款成功但订单被取消、资金进退款等待期；③ 执行方式与精度：A 分钟级延迟消息（≈24h 整点）vs B 每小时跑批（24~25h）vs C 每日跑批（24~47h）——C 方案用户第 30 小时仍能支付成功，与"24 小时"字面承诺直接矛盾，属时效承诺理解分歧而非实现自由度；④ 取消副作用范围与时效：A 同步释放库存/退券+推送 vs B 异步对账延迟释放（券小时级后可用）+仅站内信 vs C 即时释放但零通知——用户是否知道订单被取消、券何时能用，三家完全不同。
- **伪缺陷剔除**：延迟消息载体选型（MQ/Redis ZSet/DB 轮询）、调度框架选型、索引与扫描 SQL 设计、幂等并发保护实现手段、"取消中"中间态是否显式建模（三家最终行为趋同）、取消前提前提醒（三家默认一致不做）。
- **P1 实证成立**——4 组互斥假设对应原文未定义的四个执行语义（起算点、在途裁决、时效刚性、副作用范围）。已沉淀为 `场景/流程与状态/R-S17-P1.md`。

## S18 并发与幂等

### CAND-020【已验证→沉淀规则】

（N=3：服务端幂等铁律派 / 前后端双层防线派 / 小团队极简派）

> 提交订单时要防止用户重复提交。

**验证结论**：
- **冲突性假设（6 组）**：① 拦截层级：A 服务端强幂等（token/唯一索引）vs B 前端置灰+后端内容哈希去重 vs C 仅前端按钮防抖——弱网/刷新/脚本直连时，C 用户产生两笔订单两次扣款，A/B 不会；② 什么算"重复"：A 用户存在在途订单即重复（状态判定）vs B 内容相同且在时间窗内（指纹判定）vs C 点击间隔小于 1~2 秒（连击判定）——用户想再下不同地址新单：A 拦截报错，B/C 放行；③ 被拦截后的行为：A 静默返回原单 vs B 弹"请勿重复提交" vs C 静默吞掉点击——连点两次后三种命运（原单成功页/警告提示/毫无反应）；④ 网络超时重点：A 同 token 幂等返回原单 vs B 拦截提示 vs C 正常建新单——弱网重点：A 拿到原单，C 名下多一笔订单；⑤ 拦截窗口时长：A 在途订单存续期（30 分钟起）vs B 固定 5 分钟 vs C 1~2 秒——隔 10 分钟重提相同订单：A 拦、B/C 放行建第二单；⑥ 重复粒度：A 不看内容在途全拦 vs B 同 SKU+同地址才拦 vs C 只防瞬时连击——给两个不同地址买同一商品：A 被迫先处理第一单，B/C 自由下两单。
- **伪缺陷剔除**：幂等 token 存储介质（Redis/DB）、token 生成算法、后端并发控制实现（分布式锁/唯一索引/CAS）、按钮 loading 动画与 UI 形态、拦截提示文案措辞、同方案内部取值微调（B 选 3 还是 5 分钟）。
- **P1 实证成立**——原文既未定义"重复"判定口径，也未指定拦截层级与拦截后果，6 组互斥且每组用户可感知。已沉淀为 `场景/流程与状态/R-S18-P1.md`。

### REAL-002【盲区信号→增强规则】

> 为了保证感谢交互的统一性，无论哪种感谢，都取消确认 + 允许短时间内撤销感谢。让用户点一次就能完成感谢，即使误点了，也能撤销。

**来源**：https://www.v2ex.com/amp/t/1001809（V2EX 帖楼主建议段）

**回测结论**（2026-10-20）：套用 R-S16-P7 **未命中**——"短时间内"触发 F2b 互斥，但该词是**弱边界词**（未量化窗口数值，边界实际仍开放：多短？超窗后行为？对方是否收到撤回通知？全缺）。判定为**互斥条款误抑制型盲区**：强边界（"5 分钟内"）与弱边界（"短时间内"）不加区分，导致"窗口未量化+拒绝路径缺失+下游回滚缺失"形态漏报。已增强 R-S16-P7：F2b 互斥条款加**强度分级**——仅量化边界或明确拒绝行为触发互斥，弱边界词不触发。
