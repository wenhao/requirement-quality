# requirement-quality

研究**需求的有效性**：什么样的需求描述拿去开发，会产出一个"能用但不符合预期"的结果。

## 定位

本仓库产出**内容无关的需求质量扫描规则库**（按场景组织），每条规则对应"场景 × 缺陷"矩阵的一个格子，用于：

- 作为 skill / clarifier 的规则源，扫描任意需求文本，命中即指出信息缺口；
- 形成**场景 × 缺陷矩阵**（见 [知识库/调研方法论.md](知识库/调研方法论.md) 与 `覆盖矩阵.md`），空格即盲区；
- 在写需求时对照自查，避免踩坑。

## 什么算"无效需求"

凡是**描述与预期产出之间存在信息缺口**的需求，都算无效。缺陷类型体系（9 标签：P1 不完整 / P2 不可验证 / P3 主观模糊 / P4 隐含假设 / P5 歧义 / P6 不精确动词 / P7 流程断点 / P8 非原子 / P9 范围失焦）见 [知识库/缺陷标签.md](知识库/缺陷标签.md)。

## 调研方法论

整体思路：**穷举场景（外部分类学交叉对照）→ AI 穷举无效写法 → 多解实现验证 → 规则沉淀 → 真实样本回测**，详见 [知识库/调研方法论.md](知识库/调研方法论.md)。

**验证协议**（每条规则入库前的质检）：把候选需求交给 3 个背景互补的独立实现者（AI 开发者人设），各自先输出实现假设清单（IMPLEMENTATION_NOTES 式）再对比——

- **冲突性假设** ≥ 2 组（互斥且用户可感知的选择差异）= 信息缺口**实证成立**，沉淀为规则；
- 仅实现自由度差异（合理默认值，如 UI 样式、库选型）= 伪缺陷，剔除；
- 每组冲突的具体分歧（A/B/C 各自选择）记录在 [测评集/](测评集/)，是规则成立的证据。

## 规则格式

每条规则内容无关、自包含，固定段落：

```markdown
# R-<场景>-<标签> <缺陷一句话>

- **场景 / 标签 / 验证**（多解实现验证结论，一行元数据）

## 命中条件
正向特征 F（须出现的结构，每个特征附一句话内联示例说明长什么样）
+ 反向特征 B（须不出现的词类，附例）
+ 布尔判定式（附读法）
+ 判定过程示例（一段命中 + 一段不命中，逐特征核对）

## 说明
缺口实质，与具体领域 / 字段内容无关

## 误报注意
不该命中却可能命中的情况（如外部引用、分期承诺）

## 漏报注意
该命中却可能漏掉的情况（如部分约束、约束词歧义）
```

> 示例的定位：**特征的内联教学材料**（一句话示意结构，不限领域），不是需求案例——规则不依赖任何具体案例成立。

## 如何贡献

1. 新规则放入对应场景目录；文件名 = `R-<场景ID>-<标签ID>.md`，与矩阵格子一一对应；
2. 没有合适的场景目录时，先修订 [知识库/场景骨架.md](知识库/场景骨架.md) 再新建；
3. 规则须经多解实现验证（见 [调研方法论.md](知识库/调研方法论.md)）才能计入 [覆盖矩阵.md](覆盖矩阵.md)；案例原文与验证分歧记录在 `测评集/<场景组>.md`；
4. 同格已有规则时**增强**该规则（特征取并集、验证结论合并），不开新文件；
5. 规则只描述结构特征，**不引用具体需求案例**——扫任何领域的需求都适用。
