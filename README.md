# requirement-quality

研究**需求的有效性**：什么样的需求描述拿去开发，会产出一个"能用但不符合预期"的结果。

## 定位

本仓库收集**无效 / 低质量需求样本**（合成样本 + 真实写法），每一条样本记录一个需求描述的典型缺陷，用于：

- 归纳"无效需求"的共性模式，形成**场景 × 缺陷矩阵**（见 [docs/METHODOLOGY.md](docs/METHODOLOGY.md) 与 `MATRIX.md`）；
- 为 AI 辅助需求澄清（clarifier）提供负样本与训练素材；
- 在写需求时对照自查，避免踩坑。

## 什么算"无效需求"

凡是**描述与预期产出之间存在信息缺口**的需求，都算无效。典型表现：

| 缺陷类型 | 示例 |
|---|---|
| 缺少校验规则 | 描述了"表单场景"，但没说字段是否必填、格式限制、长度上限 |
| 缺少边界条件 | 未定义空态、极值、并发、异常分支的行为 |
| 缺少验收标准 | 只有功能描述，没有"做到什么程度算完成" |
| 隐含假设 | "和现有系统保持一致"——但"现有"指哪个版本、哪个行为没说 |
| 主观形容词 | "界面要美观"、"性能要流畅"，无量化指标 |
| 流程断点 | 有正常流程，未覆盖失败/回退/撤销路径 |

## 调研方法论

整体思路（穷举场景 → AI 穷举无效写法 → 多解验证 → 矩阵承载 → 真实样本回测）详见 **[docs/METHODOLOGY.md](docs/METHODOLOGY.md)**。

## 目录结构

按**场景类别**组织样本，每类一个目录，每个样本一个 Markdown 文件：

```
cases/
├── form/                 # 表单类
│   └── 2026-10-20-no-field-validation.md
├── flow/                 # 流程/交互类
├── data/                 # 数据/接口类
└── ...
```

## 样本格式

每个样本文件固定三段结构：

```markdown
# <一句话概括缺陷>

## 原始需求

> 原样摘录需求描述（脱敏后）。

## 缺陷分析

指出信息缺口在哪里、开发拿到后会怎么理解、可能产出什么偏差。

## 应补充的内容

列出该需求要变得"有效"，至少需要补充哪些信息。
```

## 如何贡献

1. 新样本放入对应场景目录；没有合适的目录就新建一个类别；
2. 文件名格式：`YYYY-MM-DD-缺陷关键词.md`；
3. 原始需求一律脱敏，去掉公司/客户/系统真实名称。
