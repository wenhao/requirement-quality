# R-S02-P1 校验需求只点名对象未定义规则

- **场景**：S02 字段级校验　**标签**：[P1-不完整](../../知识库/无效需求标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，4 组冲突性假设：核验语义/唯一性/格式严格度/失败披露）

## 命中条件

**正向特征（须出现）**：

- **F1 校验意图声明**："需要/要/支持 + 校验 / 验证 / 检查 / 合法性"类结构，或字段名 + "要有效/要合法/要规范"表述。
  - 例："**需要校验**手机号和邮箱" → F1 成立；"手机号**要真实有效**" → F1 成立。
- **F2 校验对象为字段级点名**：点名校验哪些字段（手机号/邮箱/身份证/密码…），但**未给任何规则**（正则、长度、号段、唯一性）。
  - 例："校验**手机号和邮箱**" → F2 成立（怎么算合法？未说）。
- **F3 效果承诺语**："保证 / 确保 / 必须 + 真实 / 有效 / 合法 / 规范"类效果表述，无落地定义。
  - 例："**保证**信息**真实有效**" → F3 成立（格式对就算有效？还是要验证码核验？未说）。

F1 为必要条件，F2、F3 至少满足其一。

**反向特征（须全部不出现）**：

- **B1 格式规则**：具体正则、位数、号段、字符集等格式约束。
  - 例："手机号 **11 位、1[3-9] 开头**" → B1 出现。
- **B2 唯一性定义**：唯一 / 查重 / 重复 / 已注册 类唯一性约束及其冲突行为。
  - 例："手机号**全局唯一**，重复注册**报'已被占用'**" → B2 出现。
- **B3 核验机制定义**：验证码 / OTP / 激活邮件 / 实名核验 等真实验核方式。
  - 例："通过**短信验证码**核验" → B3 出现。

### 判定

```
(F1 ∧ (F2 ∨ F3)) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S02-P1
```

判定式读法：**左边**（要校验，点名了字段或给了效果承诺）**同时右边**（格式规则、唯一性、核验机制全没定义）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "用户注册时需要校验手机号和邮箱，保证信息真实有效。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "需要校验" |
| F2 | ✓ | 点名手机号、邮箱，无规则 |
| F3 | ✓ | "保证真实有效" |
| B1/B2/B3 | ✗ | 格式/唯一性/核验全无 |

→ **命中**：实证显示"真实有效"被落地为纯格式校验（零核验、1 步注册）、双通道强核验（短信 OTP + 邮箱激活、不过不落库）、仅手机 OTP 三种互斥方案——假邮箱能否注册成功、注册后账号是否立即可用，三案完全不同。

**例 2（不命中）**：

> "注册校验：手机号 11 位 1[3-9] 开头全局唯一（重复报'已被注册'），通过短信验证码核验后方可创建账号。"

B1（11 位/1[3-9]）、B2（全局唯一+冲突行为）、B3（短信验证码）出现 → **不命中**。

## 说明

本规则检测校验类需求的**规则与核验语义缺失**，与字段领域无关（手机号/邮箱/身份证/统一社会信用代码均适用）。缺口实质：校验需求 = 格式规则 × 唯一性约束（含冲突行为）× 核验机制 × 失败反馈粒度。"保证真实有效"是 P2 不可验证的典型载体——"有效"既可解读为格式合法（静态校验），也可解读为真实验核（动态 OTP/激活），两者的实现成本与用户流程天差地别；而唯一性缺失直接决定"同一邮箱能否注册多个账号"这类账号体系根基行为。校验需求只点名对象不给规则时，开发只能按自己背景的严格度惯性填充。

## 误报注意

1. **规则外部引用**："校验规则见附录/数据字典"——B1 以外部形式存在，需人工确认文档覆盖全部点名字段；
2. **平台既有校验组件**："沿用现有 validator 组件的规则"——规则以外部形式存在，不命中；
3. **明确的分期承诺**："一期只做非空校验，完整规则二期补"——显式分期决策，不命中。

## 漏报注意

1. **部分字段有规则**：手机号给了正则、邮箱没给——B1 出现打破命中，但邮箱规则缺失仍是缺口，需按字段粒度核对（每个点名字段是否有规则归属）；
2. **有核验无冲突行为**："发短信验证码"出现 B3，但验证码通过的号码已被注册怎么办未说——B2 缺失变体；
3. **效果语口语化**："别让人乱填""把住数据关"——隐含校验意图，F1/F3 词表需覆盖管理性口语。
