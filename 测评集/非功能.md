## S33 性能与容量

### CAND-002【已验证→沉淀规则】

> 用户反馈订单列表加载太慢了，需要优化一下订单查询的性能。

**预埋缺口**：`P3-主观模糊`（"太慢""优化"无量化）；`P6-不精确动词`（"优化"）；`P9-范围失焦`（是需求还是问题陈述？优化到多少、量测口径都未定义）。

**验证结论**（2026-10-20，N=3：DBA/前端全栈/后端架构师）：**P3 实证成立**——"太慢"被解读为 SQL 执行耗时（p95>500ms）/ 白屏 LCP（<1.5s）/ 端到端接口耗时（p95<300ms）三种互斥口径；验收标准、数据规模假设（5000 万行 vs 单页 20 条 vs 5 亿）全分歧。P6/P9 为伴随特征。已沉淀为 `场景/非功能/R-S33-P3.md`。

## S34 兼容性与环境

### CAND-035【已验证→沉淀规则】

（N=3：To B 政企前端 / To C 常青浏览器前端 / 小团队务实派）

> 系统需要兼容主流浏览器。

**验证结论**：
- **冲突性假设（5 组）**：① 清单与版本下限：A IE11+国产双核+Chrome≥69 锁死 vs B 常青最新两版+Safari≥13、IE/国产忽略 vs C 不列清单脚手架默认——同一用户用 360 兼容模式打开：A 正常、B 白屏、C 凭运气；② 验收口径：A 全功能可用像素可容忍 vs B 核心链路通视觉可缺失 vs C 我的 Chrome 能跑即算——同一台旧 Safari 三份裁决相反；③ 不支持处置：A UA 检测+升级引导页 vs B 静默降级少功能无提示 vs C 白屏不管——IE11 用户分别看到引导页/悄悄少一半功能/白屏零反馈；④ 技术约束：A 禁用新特性全量转 ES5 vs B ES2020+ 自由+最小 polyfill vs C 零配置；⑤ 测试方式：A 真机+云测发布前拦截 vs B 线上监控 vs C 用户即测试。
- **伪缺陷剔除**：构建工具与 browserslist 具体写法、polyfill 选型、组件库品牌、UA vs 特征检测手段、CI 浏览器矩阵流水线。
- **P3 实证成立**——"主流"的定义分裂（①）是根因，直接派生验收（②）与处置（③）连锁冲突：一个形容词的歧义放大为三套用户可感知的系统行为。已沉淀为 `场景/非功能/R-S34-P3.md`。

## S35 易用性

### CAND-036【已验证→沉淀规则】

（N=3：C 端极简设计派 / B 端效率密度派 / 小团队默认组件派）

> 界面要简洁易用，方便用户操作。

**验证结论**：
- **冲突性假设（5 组）**：① 信息架构：A 单任务聚焦页（一屏一操作）vs B 高密度多列表格工作台（一屏尽收）vs C 标准后台模板——用户打开产品看到三种互斥的界面结构；② 导航层级：A 强制扁平 2 级、超层砍功能 vs B 3–4 级导航树+面包屑 vs C 层级不设限——A 的实现甚至会因此少掉功能；③ 操作路径：A 核心任务 3 步向导式、牺牲批量 vs B 批量+快捷键优先、单任务可 5 步 vs C 组件默认不优化步数——完成同一任务的点击数与批量能力直接可感知；④ 新手引导：A 首次分步引导浮层 vs B 预置模板工作台 vs C 空白空状态——新用户首屏三态互斥；⑤ 衡量主体：A 真实小白用户测试完成率≥90% vs B 专业效率指标+团队评审 vs C 无人评估上线看反馈——迭代方向为小白简化 vs 为专家加速 vs 不迭代。
- **伪缺陷剔除**：视觉细节（留白/字号/行高，审美自由度）、组件库品牌、暗色模式、插画图标风格、快捷键键位映射。
- **P3 实证成立**——"简洁""易用"在 C 端（减法聚焦）与 B 端（密度批量）心智中方向相反，无度量衡时由实现者自我评价裁决；隐性上游分歧：三人连目标设备（移动 vs 桌面）假设都不同。已沉淀为 `场景/非功能/R-S35-P3.md`。

## S36 可靠性与恢复

### CAND-037【已验证→沉淀规则】

（N=3：金融级 RPO=0 派 / 云原生 SRE 派 / 小团队单库派）

> 系统要稳定，不能出现数据丢失。

**验证结论**：
- **冲突性假设（5 组）**：① 可用性目标：A 99.99%（年停机 ≤53 分钟，RTO≤15m）vs B 99.9%~99.95%（RTO≤1h）vs C 99%~99.5%（宕机次日修复可接受）——用户年停机时长相差两个数量级（约 1h vs 9h vs 1–4 天）；② RPO 口径：A 同步复制 RPO=0（事务级零丢失）vs B 分钟级快照 vs C 24h 每晚备份——故障后找回数据的完整性：分毫不差 vs 丢几分钟 vs 丢一整天订单；③ 灾难覆盖：A 异地双活区域级可继续服务 vs B 同地域跨可用区（Region 级无防护）vs C 单库本地盘（机房级灾难数据全毁）；④ 成本拓扑：A 双活成本 ×3–5+写入延迟代价 vs B 多可用区 ×1.5–2 vs C 单实例 ×1——资源报价数量级差异；⑤ 误删防护：A 软删+回收站+权限+审计四层自助恢复 vs B 快照回档需 DBA 介入 vs C 无技术兜底靠运维规范——误删后自己撤回 vs 找客服等恢复 vs 永久丢失。
- **伪缺陷剔除**：数据库/存储品牌、备份工具形态（mysqldump/云快照/xtrabackup）、监控告警产品、演练频率（三家"要做演练"趋同）、复制技术细节。
- **P2 实证成立**——可靠性是有价连续谱（单实例到双活成本差 3–5 倍），无量化口径时任何一档都可自称达标，验收缺口在故障发生时才暴露且已无补救窗口。已沉淀为 `场景/非功能/R-S36-P2.md`。

## S37 国际化与时区

### CAND-038【已验证→沉淀规则】

（N=3：出海全量本地化派 / i18n 预留派 / 机翻极简派）

> 系统需要支持国际化，方便后续出海。

**验证结论**：
- **冲突性假设（6 组）**：① 范围：A 全量本地化（文案+时区+货币+合规+RTL）vs B 仅文案键值化+UTF-8 vs C 仅保证可被机翻——海外用户分别看到本地货币+合规弹窗 / 英文界面但价格时间不变 / 生硬机翻；② 语言集：A 按目标市场多语种 vs B 固定中英 vs C 动态任意语——选阿语时 A 视市场有精校版，B 直接无选项；③ 切换机制：A 区域自动检测+手动覆盖记忆 vs B 仅设置页手动 vs C 无入口依赖浏览器翻译——新海外用户首屏：自动本地语言 / 默认中文需自寻设置 / 必须自己触发翻译；④ 时区：A UTC 存储+按用户本地渲染 vs B 统一单一时区 vs C 不处理跟随服务器——海外用户查订单时间要不要心算时差；⑤ 数据层：A 分类/字典/UGC 多语言化+后台运营 vs B 结构预留 vs C 机翻连带——精校译文 / "英文界面+中文内容"混杂 / 每次刷新可能不一致；⑥ 本期达标线：A 具备多区域上线能力 vs B 文案机制就绪（零硬编码+加包即扩展）vs C 插件可翻——同一句验收对应三种交付物：多币种演示 / 新增语言包演示 / 翻译截图。
- **伪缺陷剔除**：i18n 框架选型、翻译管理平台与流程、字体字形方案、键命名规范、UTF-8 改造（三方趋同均执行）。
- **P9 实证成立**——国际化是分层谱系（薄中厚成本差一个量级），"支持国际化"无层锚定、"后续出海"无目标市场（东南亚与欧美的语言/合规/RTL 完全不同），无目标市场的国际化是无的放矢。已沉淀为 `场景/非功能/R-S37-P9.md`。

## S38 可配置与可扩展

### CAND-039【已验证→沉淀规则】

（N=3：企业个性化派 / 管理员治理派 / 小团队抽屉勾选派）

> 列表的展示字段要做成可配置的。

**验证结论**：
- **冲突性假设（6 组，①③⑤强互斥）**：① 配置主体：A 每个最终用户自主配置（列头拖拽所见即所得）vs B 仅管理员配置、普通用户只读无入口 vs C 用户自己抽屉勾选——B 方案下普通用户界面上永远不存在配置入口；② 配置范围：A 显隐+顺序+宽度/对齐+筛选器 vs B 模板级+必显字段锁定 vs C 仅显隐——用户能否拖列序调列宽：A 可以，C 永远不能；③ 生效范围：A 仅本人 vs B 管理员一改全员/角色实时生效 vs C 仅本人本机——B 中一次变更改变所有用户列表，A/C 改动他人不可见；④ 预设方案：A 角色起手视图可再改 vs B 行业模板强制下发 vs C 无模板——新用户首屏三种形态；⑤ 持久化：A 服务端跨端实时同步 vs B 配置中心版本化 vs C localStorage 本机——换设备后 A 配置仍在，C 丢失；⑥ 兜底护栏：A 自助恢复默认+最少 1 列校验 vs B 管理员锁定+版本回滚 vs C 无兜底——用户能否把列表配到关键列全隐藏：B 强制阻止，A/C 允许。
- **伪缺陷剔除**：存储表结构、拖拽库、缓存方案、配置入口形态（列头/抽屉/弹窗，交互自由度）、元数据管理方式。
- **P1 实证成立**——冲突轴心是产品政治而非技术：配置主体=权力分配（用户自治 vs 管理员治理），两种理解都合理且互斥。已沉淀为 `场景/非功能/R-S38-P1.md`。

## S39 部署与版本兼容

### CAND-040【已验证→沉淀规则】

（N=3：企业全兼容派 / SaaS 滚动升级派 / 小团队 ALTER 派）

> 新版本要兼容旧版本的数据。

**验证结论**：
- **冲突性假设（5 组）**：① 旧版本跨度：A 有史以来所有版本（LTS 降级读取链）vs B 仅上一版 N-1 vs C 上线时活着的生产数据——2019 年导出的文件能否被新版本打开，三案不同；② 兼容语义：A 只读+自动原地升级 vs B 惰性迁移触及才转 vs C 仅 schema 不报错即达标——旧数据被打开后原地升级/按需转换/停留旧格式；③ 失败处置：A 预检全量校验阻断发布 vs B 坏行隔离跳过其余上线 vs C 先 ALTER 报错再说——同一份脏数据，用户面对"升级被拒绝"/"部分功能缺数据"/"上线后报错"三种命运；④ 并行策略：A 版本标记+双格式互读 vs B 单向双写窗口 vs C 停机窗口一次性切换——不停机滚动升级时成功/数据错乱/不允许此操作；⑤ 回滚能力：A 迁移可逆（应用回退即数据回退）vs B 不可逆（回滚=备份恢复且 DBA/用户负责）vs C 无回滚概念——新版本出严重 bug 能否一键装回旧版继续干活。
- **伪缺陷剔除**：迁移工具（flyway/liquibase/手写 SQL）、ALTER 细节、迁移前快照（行业惯例趋同）、执行位置（启动时/脚本/CLI）、"兼容"默认仅指业务数据（三方趋同）。
- **P4 实证成立**——"旧版本"是写作者与特定读者间的私有共识（团队知道客户版本分布），非领域公共知识；企业客户版本分布是散点（可能停在 3 年前），跨度假设一错迁移矩阵全错。已沉淀为 `场景/非功能/R-S39-P4.md`。与 S43 分界写入规则说明：S43 是老数据搬入新系统（一次性迁移项目），S39 是新版本读得动旧数据（版本兼容能力）。
