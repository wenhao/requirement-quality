## S19 提示/通知

### CAND-021【已验证→沉淀规则】

（N=3：社交 IM 推送派 / 中后台站内信派 / 小团队极简派）

> 有新消息时通知用户。

**验证结论**：
- **冲突性假设（6 组，4 组三方互斥 + 2 组二对一）**：① "消息"所指：A 仅用户间聊天会话 vs B 仅系统事件/业务通知 vs C 全量混装——三种理解收敛为 IM 提醒/审批待办/通用收件箱三种不可互换的产品；② 通知渠道：A App 推送+角标（离线可达）vs B 仅站内信红点（不登录零感知）vs C 邮件+页内轮询——离线触达半径三级递减；③ 触发时机：A 逐条实时 vs B 站内即时+外发日摘要 vs C 定时批处理分钟级延迟；④ 点击落地：A 深链直达会话并标已读 vs B 跳转业务单据详情 vs C 统一收件箱列表——动线完全不同；⑤ 通知对象【2v1】：B 按订阅角色组全员 vs A/C 接收者本人——B 整组人被同时通知；⑥ 免打扰/频控【2v1】：A 全套（会话级静音/夜间/前台抑制）vs B/C 无——A 用户深夜安静，B/C 凌晨照样被轰炸。
- **伪缺陷剔除**：推送服务商选型、红点技术实现（轮询/WebSocket）、消息表结构、角标计数精度、已读多端同步协议、⑤中 A/C 趋同侧。
- **P9 实证成立**——"消息"与"用户"两个核心名词完全未圈定（①⑤为直接证据），属范围层缺口而非默认值差异。已沉淀为 `场景/交互反馈/R-S19-P9.md`。

## S20 确认/二次确认

### CAND-022【已验证→沉淀规则】

（N=3：C 端轻确认可撤销派 / 中后台强确认派 / 小团队极简派）

> 删除操作需要二次确认。

**验证结论**：
- **冲突性假设（5 组，3 组三方互斥 + 2 组两方对立）**：① 覆盖范围：A 仅批量/高危入口（单条免确认直接删+Toast 撤销）vs B 所有删除+全部高危操作（含注销/移除成员）vs C 恰好所有"删除"按钮不外延——用户删一条记录时 A 无拦截、B 强确认、C 原生框；② 确认形式：A 轻量弹窗一键 vs B 输入实体名称方能执行 vs C 原生 confirm——操作成本相差一个数量级；③ 可撤销性【2v1】：A 确认后 5 秒撤销+30 天回收站 vs B/C 确认即不可逆执行——误删后 A 用户可自救找回，B/C 数据即刻消失；④ 弹窗信息量：A 仅数量 vs B 级联影响明细+不可恢复警示 vs C 固定一句"确定要删除吗？"——删除前能否预知连带后果三案不同；⑤ 层级记忆【2v1】：A 会话内首次确认后可跳过 vs B/C 每次必弹——连续批量操作时 A 第二次起不被打断。
- **伪缺陷剔除**：弹窗组件选型、动画样式、按钮配色（高危红为三方惯例）、文案措辞、遮罩/Esc 行为、平台适配、已选定撤销策略后的保留时长参数。
- **P1 实证成立**——覆盖范围、确认强度、可逆性等 5 个用户可感知维度全无定义。核心缺口排序：覆盖范围 > 确认语义（可否自救）> 强度分级。已沉淀为 `场景/交互反馈/R-S20-P1.md`。

## S21 加载/进度

### CAND-023【已验证→沉淀规则】

（N=3：C 端骨架屏派 / 中后台统一规范派 / 小团队极简派）

> 页面加载要有加载状态。

**验证结论**：
- **冲突性假设（2 组，均三向互斥，恰达门槛）**：① 加载态形态：A 整页骨架屏灰块占位 vs B 全屏居中 spinner 遮罩 vs C 顶部细进度条——用户进入页面第一眼看到"灰块内容预告/白屏中央转圈/顶端一根进度条"，三种心智模型完全不同；② 覆盖范围：A 首次进入+路由切换（局部刷新用内联骨架）vs B 所有数据请求含局部刷新（任何请求都转圈）vs C 仅浏览器首次进入（页内操作零反馈）——点击搜索/刷新后分别看到"局部灰块/全屏遮罩/毫无反应"。
- **伪缺陷剔除**：延迟展示策略（A/C 立即展示，B 200ms 延迟，2:1 收敛为规范派合理默认）、超时兜底（A/B 均做 ~10s 兜底仅形式差异，C 缺失但非三向互斥）、加载中可否操作（A/C 不阻断，2:1）、spinner 样式/动画库/组件封装——纯自由度。
- **P3 实证成立**——"加载状态"为主观泛指词，形态与范围两大决策维度三向分叉且均不可对照验收。本轮冲突组数（2 组）为历轮最低，印证交互反馈类场景默认值收敛度高于流程类。已沉淀为 `场景/交互反馈/R-S21-P3.md`。

## S22 空态/首次使用

### CAND-024【已验证→沉淀规则】

（N=3：C 端增长转化派 / 中后台区分态派 / 小团队极简派）

> 列表为空时展示空状态页面。

**验证结论**：
- **冲突性假设（5 组）**：① 空态是否承载行动入口：A 插画+利益点文案+主 CTA（新建/导入）vs B 按态情境化操作 vs C 纯文案"暂无数据"无事可做；② 筛选空与真空是否区分：A 统一空态并引导新建 vs B 严格区分+一键"清除筛选" vs C 统一"暂无数据"——搜索无结果时 B 用户一键找回列表，A 用户被误导去新建（实际是筛选问题），C 用户手动逐个清条件；③ 是否兼任首次使用引导：A 空态即 onboarding（附模板/示例）vs B 明确否只陈述事实 vs C 无此概念——新用户首次进入看到带引导转化页 vs 一行状态说明；④ 权限不足/加载失败归属：A/C 混入空态兜底 vs B 独立无权限页+错误重试页——无权限用户在混入方案下误以为"自己没数据"，断网时 C 用户误判数据丢失；⑤ 行动按钮指向：A 新建/导入（增长转化）vs B 按态分配（清除筛选/联系管理员）vs C 不设。
- **伪缺陷剔除**：插画风格、文案措辞、组件库选型（antd Empty vs 自研）、布局粒度（整页 vs 列表区域，原文"页面"可收敛）、动效装饰。
- **P1 实证成立**——空态职责边界（陈述/转化/教育）、"空"的语义口径（真空/筛选空/无权限/失败）、异常态归属均未界定。已沉淀为 `场景/交互反馈/R-S22-P1.md`。
