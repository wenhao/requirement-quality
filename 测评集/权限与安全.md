## S23 角色与权限

### CAND-025【已验证→沉淀规则】

（N=3：企业级 RBAC 架构师 / SaaS 订阅开关派 / 小团队极简派）

> 系统需要支持权限管理。

**验证结论**：
- **冲突性假设（5 组）**：① 权限模型形态：A 客户可自定义角色的 RBAC 矩阵 vs B 订阅档位×功能开关（权限=买没买）vs C 硬编码两档不可扩展——客户能否自助新增"财务专员"身份三案不同，B 用户被拦时提示"升级套餐"；② 管控层级：A 页面+按钮+接口+数据四层 vs B 模块+页面两层 vs C 仅接口+菜单显隐——A 会出现"页面可见但删除按钮置灰"的中间态，B/C 要么整页消失要么全功能可用；③ 管理主体：A 管理界面可下放部门管理员 vs B 平台管套餐+租户管成员双层 vs C 无界面改库指定——人员变动时 A/B 客户界面上点选完成，C 必须找开发改数据库；④ 数据范围与组织：A 按部门树隔离（仅本人/本部门及以下）vs B 租户内全员共享 vs C 全局共享无组织概念——普通销售在 A 只看到自己的客户，B/C 看到全部；⑤ 变更审计：A 全量权限变更+操作审计 vs B 仅订阅事件 vs C 无审计——越权事件 A 能出具完整记录，C 无法追责。
- **伪缺陷剔除**：权限表结构、框架选型（Casbin/Spring Security）、缓存方案、生效时机技术路径、后端接口校验（三方均做）、新用户默认最低权限（趋同）、认证方式 JWT/Session（超出本需求边界）。
- **P9 实证成立**——"权限管理"四字未限定管控对象、层级、粒度、管理主体，三种解读收敛为 RBAC 平台/功能开关/固定两档三种互斥产品。已沉淀为 `场景/权限与安全/R-S23-P9.md`。

## S24 登录/认证

### CAND-026【已验证→沉淀规则】

（N=3：C 端账号风控派 / 企业 IT 管控派 / 小团队极简派）

> 用户可以通过手机号验证码登录。

**验证结论**：
- **冲突性假设（5 组，2 组含二对一结构）**：① 未注册手机号行为：A 发码+验证通过静默建号（新号受限）vs B 不发码报"账号不存在，请联系管理员"（开户权归 IT）vs C 发码+验证通过即建号直进全功能——未注册用户在 B 根本收不到短信；② 存量老账号冲突：A 检测冲突弹"绑定/新建"引导页 vs B 通道仅对管理员预绑定账号开放 vs C 不检测直接新建平行账号——老用户在 A 看到引导页、B 报错、C 被静默送进空账号（历史数据"消失"）；③ 封禁账号【A/B 拒绝趋同 vs C 放行】：C 无账号状态概念，被封禁用户照常登录；④ 多设备策略：A 多端并行+设备管理+异地提醒 vs B 单会话踢旧设备+短时效 vs C 长效 token 无管理——第二台设备登录瞬间 B 旧设备被强制下线；⑤ 前置人机校验【A 有 vs B/C 无】：A 滑块+日发码上限+错误锁定，B/C 直接收码。
- **伪缺陷剔除**：验证码位数（三人皆 6 位趋同）、有效期（5/5/10 分钟同量级默认）、存储与加密方案、短信服务商、接口风格、锁定时长参数。
- **P1 实证成立**——原文只约束了"手机号+验证码"动作，未约束账号体系边界（谁允许有账号、老账号怎么办、封禁账号怎么办）；冲突集中在账号语义而非验证码参数。已沉淀为 `场景/权限与安全/R-S24-P1.md`。

## S25 数据权限/隔离

### CAND-027【已验证→沉淀规则】

（N=3：CRM 归属权派 / 组织架构范围派 / 小团队极简派）

> 业务员只能看到自己的客户数据。

**验证结论**：
- **冲突性假设（6 组）**：① "自己的客户"定义：A 被分配为负责人才算（owner_id）vs B 我所在部门范围内都算 vs C 我创建的都算（created_by）——小张创建客户后转给小王：C 下小张仍可见，A 下不可见，B 下整组可见，同一页面三张列表；② 上级可见性：A 默认不能需单独授权 vs B 组织树天然可看 vs C 主管无特殊逻辑——销售总监打开页面：B 显示全团队 2000 条，A/C 显示 0 或 3 条；③ 协作场景：A 临时授权+到期收回 vs B 范围调整长期共享 vs C 不支持——共同跟进大客户：A 可设 30 天临时可见，C 直接告知"做不到"；④ 离职交接：A owner 变更即失明 vs B 移出组织树失明 vs C 主表转移但历史跟进记录仍残留可见——交接次日原业务员登录，C 下时间线仍残留；⑤ 公共客户池：A 全员可见可申领 vs B 按部门归属本部门可见 vs C 对所有业务员不可见——新员工首日：A 看到 500 条可申领，C 看到空白页；⑥ 操作面：A/B 全表面隔离（列表/详情/搜索/导出）vs C 仅列表过滤、详情按 ID 直查不设防——拿到同事客户 ID 直接访问详情：A/B 返回 403，C 能打开完整资料并导出（越权缺陷级差异）。
- **伪缺陷剔除**：SQL 过滤实现（WHERE/拦截器/SDK）、索引与缓存、权限位挂载方式、申领并发锁、越权尝试审计（附加项）。
- **P1 实证成立**——归属定义（owner/creator/org-scope 三模型三个系统）、角色矩阵、操作面边界、例外态全无交代；组⑥为信息缺口转化为越权安全缺陷的直接证据。已沉淀为 `场景/权限与安全/R-S25-P1.md`。

## S26 审计/日志

### CAND-028【已验证→沉淀规则】

（N=3：金融级全量留痕派 / SaaS 业务事件派 / 小团队极简派）

> 关键操作要记录日志。

**验证结论**：
- **冲突性假设（6 组）**：① "关键操作"范围：A 全部写操作+敏感读 vs B 仅删除/导出/权限变更等高敏动作 vs C 所有 HTTP 请求（access log 粒度）——普通资料编辑在 A 留痕、B 无痕、C 只有一条无业务含义的 URL；② 内容要素：A 含改前/改后值可还原现场 vs B 人话描述+IP+成败 vs C 仅方法/路径/状态码——"谁改了我的数据"，A 能答"从 X 改成 Y"，C 答不出动了什么；③ 可见性：A 独立审计权限双人授权（业务管理员不可见）vs B 管理后台自助可查 vs C 无界面仅服务器 grep——租户查自己组织记录，B 自助，A/C 须找平台方；④ 留存期限：A 永久/≥5 年 WORM vs B 1 年 vs C 随日志滚动 14–30 天——半年后翻旧账，C 的日志已滚没；⑤ 失败记录：A 成败都记且区分"未遂" vs B 只记成功 vs C 仅凭 4xx 无语义——反复尝试越权导出被拒，A 留下未遂线索，B 完全无痕；⑥ 证据效力：A 防篡改签名导出可作合规证据 vs B CSV 运营用途 vs C 无导出——监管检查时 A 出具可验证证据，C 什么都拿不出。
- **伪缺陷剔除**：存储选型（DB/ELK/文件）、同步 vs 异步写入、字段命名与格式、分表归档、实现机制（AOP/中间件）、trace_id 冗余字段。
- **P1 实证成立**——"关键操作"自我指涉（用什么标准判断关键本身就要定义）+ 审计价值兑现滞后（出事才发现该记的没记），6 维度全开放。已沉淀为 `场景/权限与安全/R-S26-P1.md`。

## S27 数据安全与防护

### CAND-029【已验证→沉淀规则】

（N=3：金融国密合规派 / SaaS 云 KMS 派 / 小团队 TDE 极简派）

> 敏感数据要加密存储。

**验证结论**：
- **冲突性假设（6 组，含 3 组二对一结构）**：① 加密层级【A/B 应用层字段级趋同 vs C 透明存储层 TDE】：拖库或备份泄露时 A/B 的身份证/手机号是密文乱码，C 打开即全部明文；② 覆盖范围：A 全 PII 枚举逐字段（含身份证/银行卡/姓名）vs B 仅凭证哈希+手机号/邮箱业务键 vs C 不区分字段整库一锅端——同一份库文件，身份证在 A 密文、B 可能未覆盖、C 明文；③ 可检索性【A/B 密文精确匹配趋同 vs C 明文全功能】："按姓名模糊搜/手机号尾号搜"在 C 有，A/B 上线即消失；④ 展示脱敏：A 默认打码+明文需权限审批审计 vs B/C 原文展示——客服打开用户详情，A 看到 138\*\*\*\*要走审批，B/C 直接看完整号码；⑤ 密钥管理【A/B 应用层可轮换趋同 vs C 零密钥】：密钥泄露应急时 A/B 换钥重加密，C 无可操作对象，密评问"密钥如何轮换"无法应答；⑥ 历史回填：A 停机全量+明文销毁 vs B 双写渐进回填 vs C 无需回填——B 上线后一段时间老数据仍明文（保护状态不一致）。
- **伪缺陷剔除**：SM4 vs AES-256-GCM（同为字段级可逆）、SM3/bcrypt/argon2（同为凭证哈希）、密码机 vs 云 KMS、HMAC 影子列 vs 确定性加密路径、加密库、IV 策略、轮换周期数值。
- **P4 实证成立**——"敏感数据"是判定负载词（预设判定已完成但标准因人而异），三个读者各持不同敏感清单，产出三个安全水位完全不同的系统；加密方式分歧还反向破坏业务功能（模糊搜索消失）。已沉淀为 `场景/权限与安全/R-S27-P4.md`。

## S28 隐私与合规

### CAND-030【已验证→沉淀规则】

（N=3：个保法逐条落地派 / GDPR 出海派 / 小团队务实派）

> 系统要符合个人信息保护的要求。

**验证结论**：
- **冲突性假设（7 组，1 组二对一）**：① 法域与义务集：A 个保法全量（知情同意/最小必要/可携带）vs B GDPR（被遗忘权/DPO/数据出境 SCC）vs C 行业通行做法（隐私政策+注销即达标）——B 注册流程多出"跨境传输授权"节点和 DPO 联系页；② 同意机制：A 分项勾选+敏感信息单独同意 vs B 明确 opt-in+可随时撤回+拒绝不降级 vs C 注册即一揽子同意——拒绝营销授权后 B 正常用全部功能、A 部分不可用、C 没有拒绝入口；③ 主体权利落地：A 查询/更正/删除/注销+导出五项 vs B GDPR 六项（含限制处理/反对权）+30 天时限 vs C 仅注销+更正走人工客服——设置页有无"导出我的数据"按钮三案不同；④ 保留与删除：A 法定期限届满自动删 vs B 请求驱动擦除+目的达成即停存 vs C 永久保留注销仅逻辑标记——注销后回访能否"找回"账号；⑤ 第三方告知：A 清单+提供前单独同意弹窗 vs B 名单+随时反对开关+DPA vs C 一句话概括——能否看到第三方名单并关闭某类共享；⑥ 未成年人：A 14 岁+监护人同意 vs B 16 岁+强制年龄验证 vs C 不验证+声明免责——注册是否强制填出生日期；⑦ 政策版本【A/B 阻断式重新同意趋同 vs C 公告+视为同意】——政策更新后是否被强制弹窗确认。
- **伪缺陷剔除**：隐私政策文案措辞、弹窗 UI、法务流程、内部安全工程基础项（TLS/存储/访问控制——三方共识）、日志保留天数参数、年龄验证技术手段（门槛年龄才是冲突）、政策历史版本页。
- **P4 实证成立**——"要求"隐含法域假设（个保法/GDPR/等保义务集互不包含），验收方是监管不是产品，漏项即违规；出海/外资/多地域业务下"国内当然按个保法"的假设最常失效。已沉淀为 `场景/权限与安全/R-S28-P4.md`。
