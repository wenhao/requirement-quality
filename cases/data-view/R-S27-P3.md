# R-S27-P3 性能需求主观无量化

- **场景**：S27 性能与容量　**标签**：[P3-主观模糊](../../docs/DEFECTS.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，分歧：量测口径三种互斥定义/验收标准/优化范围/数据规模假设全分歧）

## 命中条件

**正向特征（须出现）**——每个特征附匹配示例，示例仅示意结构，不限领域：

- **F1 性能主诉**：出现慢/卡/延迟/耗时/响应慢 + 用户反馈/投诉/体验差 类表述。
  - 例："用户反馈订单列表**加载太慢**了" → F1 成立。
- **F2 非量化优化动词**：优化 / 提升 / 加快 / 改善 / 提速，后接性能/速度/体验类宾语，且**不带任何数字指标**。
  - 例："需要**优化**一下订单查询的**性能**" → F2 成立。

**反向特征（须全部不出现）**：

- **B1 量化指标**：具体数字 + 单位（ms / s / QPS / 并发数 / p95 / p99 / %）。
  - 例："接口 p95 **< 300ms**" → B1 出现，不命中。
- **B2 量测口径**：白屏时间 / 首屏 / LCP / 接口耗时 / SQL 耗时 / 吞吐 等指明测什么的词。
  - 例："以**接口耗时**为准" → B2 出现，不命中。
- **B3 基线与场景**：当前值 / 基线 / 压测 / 数据量 / 并发规模 等量测前提。
  - 例："当前 **p95 为 800ms**，**单表 5000 万行**场景下优化" → B3 出现，不命中。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S27-P3
```

判定式读法：**左边**（有性能抱怨 + 有优化动作，但全是主观词）**同时右边**（没数字、没口径、没前提）→ 命中。反向特征是灭火器：出现任何一个，无论正向多完整都不命中。

### 判定过程示例

**例 1（命中）**：

> "用户反馈订单列表加载太慢了，需要优化一下订单查询的性能。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "加载太慢" |
| F2 | ✓ | "优化…性能" |
| B1 | ✗ | 无任何数字指标 |
| B2 | ✗ | 未说测什么 |
| B3 | ✗ | 无当前值/规模前提 |

→ **命中**：性能主诉无量化目标、无量测口径，开发各自设定目标与方案。

**例 2（不命中）**：

> "订单列表接口 p95 耗时 800ms，需优化到 300ms 以内，单表 5000 万行。"

B1（800ms/300ms）、B2（接口耗时/p95）、B3（5000 万行）全部出现 → **不命中**。

## 说明

本规则检测性能类需求的**量化缺失**，与性能问题领域无关（接口/页面/查询/任务均适用）。缺口实质：性能目标 = 量化指标 × 量测口径 × 场景前提，三者缺一，开发只能自行设定——验证实证显示三位不同背景开发者对同一句"太慢"给出了三种互斥定义（SQL 执行耗时 / 首屏白屏时间 / 端到端接口耗时），优化方向随之完全不同（调索引 / 改渲染 / 上缓存），且无共同验收标准判断"优化完成"。

## 误报注意

1. **分期测量承诺**："先优化，具体指标待压测后定"且有明确压测计划时不命中——量化被显式后置且有路径；
2. **外部指标引用**："性能目标见 SLA 文档"不命中——指标在外部文档，需人工确认覆盖；
3. **非功能性闲笔**：性能抱怨只是背景陈述，需求主体是别的功能时不命中，应扫主体。

## 漏报注意

1. **伪量化**："要快""要流畅""毫秒级""秒开"等口语化指标不构成 B1（"毫秒级"无具体数值与口径）——注意这类词出现时 F2 实质仍成立，规则应命中；
2. **只给数字不给口径**："优化到 500ms 以内"有 B1 但无 B2（测接口还是测白屏？）——口径缺失仍是缺口，可命中本规则或其变体；
3. **量测口径词作动词**："测量一下哪里慢"是排查任务不是性能需求，需先区分需求/任务性质。
