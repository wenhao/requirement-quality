## S40 范围/优先级

### CAND-041【已验证→沉淀规则】

（N=3：MVP 原教旨派 / 企业交付派 / 全栈多面手；背景：需求文档已零散列出下单/支付/优惠券/评价/客服/报表等功能点，无优先级标注）

> 本期先做核心功能，其他功能后续迭代。

**验证结论**：
- **冲突性假设（8 组）**：① 核心圈定口径：A 最小可收费闭环（2 个功能）vs B 合同/SOW 承诺清单（5 个）vs C 架构全打通全做简化版（6 个）——首版功能数量 2/5/6，用户一眼可见；② 优惠券：A 不做无入口 vs B 完整版（演示亮点）vs C 仅满减——结账时有无抵扣入口；③ 评价：A 不做 vs B 只读预置数据 vs C 星级文字可写；④ 客服：A/B 不做（人工/合同未列）vs C 站内留言板——用户有无站内求助入口；⑤ 报表：A 不做查库 vs B 完整看板（验收会领导要看）vs C 一张统计页——老板看数据求人还是点页面；⑥ 后续时间锚点：A 无期限 backlog 按数据决定 vs B 二期合同时间表 vs C 下版即增强——被砍功能何时能用上的承诺完全不同；⑦ 变更处理：A 一律拒绝范围冻结 vs B 变更单签字可插期 vs C 小需求顺手做掉；⑧ 争议裁决：A 真实交易跑通即过 vs B 合同清单逐项核验缺项即不过 vs C 全流程点通即过——同一份交付物三种相反裁决。
- **伪缺陷剔除**：backlog 管理工具、排期方法（里程碑/迭代节奏）、登录实现方式、演示数据预置、客服轮询 vs WebSocket。
- **P9 实证成立**——"核心"无圈定口径、"后续"无锚点、无变更与裁决依据，三种切法都真诚执行了"核心"，首版交付物相差 3 倍；S40 是范围失焦的**源头形态**（写范围的地方都失焦）。已沉淀为 `场景/需求管理/R-S40-P9.md`。

## S41 验收/成功标准

### CAND-042【已验证→沉淀规则】

（N=3：质量工程派 / 业务交付派 / 小团队自测派）

> 功能做完后要能正常使用，达到可上线的程度。

**验证结论**：
- **冲突性假设（8 组）**：① "正常使用"口径：A 全功能含边界/异常流无已知缺陷 vs B 主流程能走通 vs C 自己点一遍不报错——边缘功能（退款/异常输入/并发）在 B/C 交付物上直接报错；② 测试深度：A 单测+集成+E2E 自动化全量+覆盖率门禁 vs B 手工全量+演示路径冒烟 vs C 仅自测冒烟——回归缺陷在 C 要用户踩到才暴露；③ 性能门槛：A 压测达标硬门槛 vs B 演示不卡即可 vs C 无要求——高峰期 C 崩溃 A 稳定；④ 安全门槛：A 扫描通过才可上 vs B 推到后续迭代 vs C 完全不评估——B/C 可能带注入/越权漏洞上线；⑤ 数据正确性：A 迁移/计算全量比对 vs B 主流程抽验 vs C 肉眼两眼——订单金额算错在 C 直达用户；⑥ 监控回滚：A 告警就位+回滚演练 vs B 预案口头约定 vs C 无监控靠热修——故障发现与恢复时长差数量级；⑦ 验收主体：A 测试+产品双签字 vs B 老板演示拍板 vs C 开发者自评——C 无独立把关，理解偏差直达全部用户；⑧ 缺陷阻断：A P2+ 全阻断回归再上 vs B 仅主流程阻断型拦下 vs C 带伤上线线上热修。
- **伪缺陷剔除**：测试框架与用例管理工具、冒烟用例条目设计、CI/CD 流水线形态、测试报告格式、缺陷记录载体。
- **P2 实证成立**——验收标准不可验证时判定权自动转移到实现者自我评价，"做完"时刻被提前，未验证缺陷面全部转嫁给用户；S41 是 P2 的根因案例（S36/S11 是它在具体维度的投影）。已沉淀为 `场景/需求管理/R-S41-P2.md`。
