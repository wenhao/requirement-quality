# R-S04-P1 文件上传未定义格式大小与生效链路

- **场景**：S04 富文本/文件上传　**标签**：[P1-不完整](../../知识库/无效需求标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，7 组冲突性假设：裁剪/生效链路/大小/格式/频率/URL 策略/入口）

## 命中条件

**正向特征（须出现）**：

- **F1 上传功能声明**："做一个/需要/支持 + 上传 + 图片/文件/附件/头像/图片"类结构。
  - 例："**做一个**图片**上传功能**，用户可以**上传头像**" → F1 成立。
- **F2 限制与处理全缺席**：上传物无任何格式、大小、数量限制表述，也无裁剪/生效/失败处理说明。
  - 例：全文无"格式/大小/限制/裁剪/审核"任一词 → F2 成立。

F1 与 F2 须同时出现。

**反向特征（须全部不出现）**：

- **B1 格式或大小限制**：格式白名单（JPG/PNG…）或大小上限（≤x MB）任一出现。
  - 例："仅支持 **JPG/PNG，不超过 5MB**" → B1 出现。
- **B2 处理链路定义**：裁剪 / 压缩 / 审核 / 生效时机（上传即生效 vs 提交后生效）任一说明。
  - 例："上传后**自动压缩**至 500KB，**提交后生效**" → B2 出现。
- **B3 失败或超限处理**：超限/失败的反馈与行为定义。
  - 例："超限**提示并拒绝**，失败可**重试**" → B3 出现。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S04-P1
```

判定式读法：**左边**（要上传，但限制与处理全没说）**同时右边**（格式大小、处理链路、失败处理全没定义）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "做一个图片上传功能，用户可以上传头像。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "做一个…上传功能" |
| F2 | ✓ | 无任何限制与处理表述 |
| B1/B2/B3 | ✗ | 格式大小/链路/失败全无 |

→ **命中**：实证显示 7 组冲突性假设——同一张 5MB 手机原图，A（10MB 上限+自动压缩）成功、B/C（2MB 上限）失败；iPhone 用户直传 HEIC 原图，A 成功、C 报"格式不支持"；脸偏一侧的照片，A 用户自选裁剪、B 原样展示、C 服务端中心裁剪可能裁掉半张脸。

**例 2（不命中）**：

> "头像上传：仅支持 JPG/PNG，不超过 2MB，选图后进入方形裁剪，上传成功即生效，超限提示具体原因。"

B1（JPG/PNG/2MB）、B2（方形裁剪/即生效）、B3（超限提示）出现 → **不命中**。

## 说明

本规则检测上传类需求的**限制与处理链路缺失**，与上传物领域无关（头像/附件/资质证书/富文本图片均适用）。缺口实质：上传需求 = 格式白名单 × 大小上限（含超限行为）× 处理链路（裁剪/压缩/审核/生效时机）× 失败处理。上传是"限制缺席"型缺口的典型——功能语义（能传文件）看似完整，但限制值是任意的：宽松实现几乎不拒绝任何文件，严格实现拒绝半数真实用户文件（HEIC 是 iPhone 默认格式，拒收等于拒绝 iPhone 用户）。生效链路分歧最隐蔽：上传即生效、提交后生效、审核后生效三种语义下，用户"选完图"后的界面表现完全不同。

## 误报注意

1. **通用上传组件**："上传走公司统一文件服务，限制按平台默认"——B1/B3 以外部形式存在，需人工确认默认值适用本场景；
2. **内部可信用户**：上下文为纯内部系统且用户可信时，审核/安全链路分歧弱化，但格式大小分歧仍在，不整体豁免；
3. **主体不是上传**："上传列表加个删除按钮"——上传已定义，主体是删除，不命中。

## 漏报注意

1. **只有格式或只有大小**："支持 JPG"但无大小——B1 出现打破命中，大小与链路缺失仍是缺口，需逐要素核对；
2. **伪限制**："支持常见格式""大小合理即可"——"常见/合理"不构成白名单与上限，应仍命中；
3. **富文本内嵌上传**："编辑器里能插图"——隐式上传需求，F1 词表需覆盖富文本/编辑器语境。
