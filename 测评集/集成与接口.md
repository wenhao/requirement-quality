## S29 第三方 API 集成

### CAND-031【已验证→沉淀规则】

（N=3：支付系统资金一致性派 / 中小商户快速接入派 / 小团队极简派）

> 对接微信支付，用户可以在线支付订单。

**验证结论**：
- **冲突性假设（7 组）**：① 取消/中途退出处置：A 超时自动关单+关单后禁止再付 vs B 永不关单同单号随时重付 vs C 不关单每次重付生成新支付单——C 用户可能对同一订单付两次钱且退款不知退哪笔；② 失败/超时未回调补偿：A 服务端每 30s 主动查单自动修复 vs B 仅用户返回订单页时查一次 vs C 无补偿纯等回调——回调丢失时 C 用户已扣款但订单永远"待支付"；③ 生效确认路径：A 服务端驱动+前端轮询秒级跳成功页 vs B 返回即见 vs C 手动刷新才见；④ 退款路径：A 用户端申请+商家审核+状态可查 vs B 仅商户后台人工发起 vs C 不做在线退款全走客服线下——订单内有无退款记录三案不同；⑤ 对账：A 每日逐笔+差错告警 vs B 财务月度人工总额 vs C 不做——掉单时 A 最迟 T+1 自愈，C 不投诉则永不发现；⑥ 重复回调幂等：A 唯一约束+状态机强幂等 vs B 先查后更新弱幂等 vs C 无幂等——微信回调重试时 C 可能重复发货/重复开通权益；⑦ 订单生效语义：A 通用状态机支付仅推进 vs B 实物订单触发发货 vs C 虚拟订单即完成交付——付完钱后用户看到的订单形态完全不同。
- **伪缺陷剔除**：支付 API 场景选型（JSAPI/Native/APP，由端类型决定）、SDK 语言、验签与证书管理实现、回调应答格式、金额精度处理、out_trade_no 生成规则、回调处理架构、中间件选型。
- **P7 实证成立**——②③④⑤⑥全部位于支付主流程之外的关键分支，原文零定义；逆向链路缺口直接等于资金风险（重复回调无幂等=重复发货，无对账=掉单永不发现）。已沉淀为 `场景/集成与接口/R-S29-P7.md`。

## S30 数据同步/接口约定

### CAND-032【已验证→沉淀规则】

（N=3：企业集成契约派 / SaaS 中间件派 / 小团队直写派）

> 和现有 ERP 系统对接，订单数据自动同步到 ERP。

**验证结论**：
- **冲突性假设（6 组，3 组三方互斥 + 3 组两方对峙）**：① 字段范围：A 全字段（主表+明细+金额+状态+客户编码）vs B 核心字段（单号/金额/状态）明细后续迭代 vs C 订单主表不含明细——ERP 侧能否看到商品行明细、按明细入库开票；② 触发时效：A 下单即推秒级 vs B 视 ERP 接口能力实时或轮询（时效不承诺）vs C 固定 5 分钟批量——库存扣减与财务口径滞后窗口差一个数量级；③ 失败兜底：A 重试退避+死信人工队列+T+1 对账 vs B 中间件自动补试+失败面板 vs C 仅记日志无告警——长期静默漏单用户感知为"ERP 少单"；④ 方向：A 双向（ERP 审核发货状态回传）vs B/C 单向——业务系统订单状态会不会随 ERP 自动流转，还是人工两头改；⑤ 历史范围：A 存量一次性初始化+增量 vs B/C 上线起增量——ERP 查不查得到历史订单，历史报表完整与否；⑥ 映射维护方：A ERP 主数据方维护对照表 vs B 集成方中间件自助配置 vs C 代码硬编码——新增商品/客户后自动生效还是持续产出"编码不存在"失败单。
- **伪缺陷剔除**：中间件/通道形态（iPaaS/RPA/直连库表）、MQ 选型、定时框架、接口协议（REST/SOAP，由 ERP 决定）、重试参数、幂等实现方式、ERP 品牌（已定环境）。
- **P4 实证成立**——"现有 ERP""订单数据""自动"三个词各自隐含整套上下文（哪套系统/什么字段/什么时效），六要素契约全部零约定。已沉淀为 `场景/集成与接口/R-S30-P4.md`。

## S31 消息推送/回调

### CAND-033【已验证→沉淀规则】

（N=3：开放平台可靠性协议派 / 业务够用派 / 小团队极简派）

> 支付成功后通过 Webhook 通知业务系统。

**验证结论**：
- **冲突性假设（6 组）**：① 失败重试：A 指数退避 10 次+死信告警 vs B 固定 3 次放弃等 T+1 对账 vs C 不重试仅打日志——接收方宕机 1 小时，A 通知必达可查，B/C 直接丢失；② 安全验证：A 强制 HMAC 签名+时间戳+nonce 防重放 vs B 仅 HTTPS vs C 无验证（至多静态 token）——攻击者可向 B/C 端点**伪造"支付成功"通知实现未付款发货**；③ 内容格式：A 结构化事件信封+全量支付字段 vs B 订单号+状态+金额摘要 vs C 极简信号 {orderId, paid}——接收方凭通知一次入账 vs 必须二次回查，集成契约互斥；④ 重复/乱序：A at-least-once+event_id 显式幂等 vs B 假定 exactly-once 按订单号覆盖 vs C 不处理反查为准——上游补发同一事件，B 的非幂等消费方（加余额）重复执行造成资损；⑤ 地址管理：A 开放平台控制台自助配置+连通性探测 vs B 部署配置文件改动需发版 vs C 代码常量硬编码——换回调地址 A 自助即时生效，B/C 产生通知中断窗口；⑥ 长期不可用：A 死信告警+补偿查询 API 双通道 vs B T+1 对账人工修复 vs C 丢弃靠业务侧轮询兜底。
- **伪缺陷剔除**：HTTP 库、传输载体（三方均默认 HTTP POST 趋同）、重试队列实现载体、幂等技术手段（唯一索引 vs SETNX——"是否设计幂等契约"是冲突④已保留）、签名算法具体选型、schema 工具、监控面板、代码分层。
- **P1 实证成立**——②（可伪造）与④（无幂等）叠加构成"伪造通知→重复入账"复合资损链路（实证中 B+C 组合正是此路径），最高优先级缺口；异步契约是双方协议，发送方未定义则接收方无从配合，联调时才发现契约真空是回调类需求最常见返工原因。已沉淀为 `场景/集成与接口/R-S31-P1.md`。

## S32 多端适配

### CAND-034【已验证→沉淀规则】

（N=3：跨端架构一套核心派 / 产品型端分工派 / 小团队 H5 壳派）

> 需要支持 App 和小程序双端。

**验证结论**：
- **冲突性假设（6 组）**：① 功能覆盖：A 双端 100% 对齐同一 feature 矩阵 vs B 小程序精简版（裁掉会员/深度功能）+App 全功能 vs C 同一套 H5 全量——小程序用户能否用全部功能，B 的用户在小程序找不到部分功能入口；② 支付渠道：A 双端统一仅微信支付 vs B App 微信+支付宝多通道、小程序仅微信 vs C 小程序 webview 内支付受限需跳转降级——App 能否用支付宝、小程序能否一路付完；③ 登录身份：A 双端微信授权同一身份（unionid）vs B 小程序微信静默+App 手机验证码 vs C 双端手机验证码——换端使用是否被迫换登录方式、能否识别为同一人；④ 发布节奏：A 双端同版本号同步发版 vs B 小程序周更试错、App 月更大版本 vs C H5 热更即时生效——同一新功能双端上线时间差可达数天至数周；⑤ 端间裁决：A 端间平行不引导 vs B 以 App 为准+小程序主动弹"下载解锁完整版"+客服同口径 vs C 无端间概念——小程序用户是否被持续引导跳转、投诉归责口径不同；⑥ 页面形态：A/B 端级原生渲染 vs C webview 网页级加载（含小程序审核被拒风险）——页面是否白屏转圈、弱网可用性。
- **伪缺陷剔除**：账号互通方向本身（三人均假设同一账号体系，趋同）、多端框架选型（uni-app/Flutter/RN）、UI 组件库、性能优化手段、数据同步技术方案、壳热更机制。
- **P9 实证成立**——六组冲突全部由"支持"一词的开放解释直接派生（全对齐/分工/同页面三种产品），无一组来自实现自由度，P9 判定证据纯净。已沉淀为 `场景/集成与接口/R-S32-P9.md`。
