# 收货地址表单未定义字段规则与目标平台

## 原始需求

> 做一个收货地址管理页面，用户可以添加和编辑收货地址，地址信息包括联系人、手机号、省市区和详细地址。

## 缺陷分析

需求只列了字段名和"添加/编辑"两个动作，关键决策点全部缺失，开发只能自行假设。三个独立 AI 开发者（React 后台风格 / Vue H5 风格 / Java 后端风格）各自实现，**5 处用户可感知分歧**为信息缺口实证：

| # | 决策点 | 开发者 A | 开发者 B | 开发者 C | 缺口根源 |
|---|---|---|---|---|---|
| 1 | 表单布局 | Modal 弹窗 | 独立路由页 | Modal 弹窗 | **目标平台未定义**（Web 后台 / H5 / 小程序？） |
| 2 | 姓名长度上限 | 2–25 字符 | 2–20 字符 | 2–20 字符 | 长度规则缺失 |
| 3 | 详细地址下限 | ≥5 字 | ≥5 字 | 无下限 | 边界规则缺失 |
| 4 | 手机号 +86/座机 | 拒绝 | 拒绝 | 归一化剥离 | 格式口径缺失 |
| 5 | 姓名字符限制 | 中英空格· | 中英空格· | 禁 Emoji（防面单乱码） | 字符集规则缺失 |

另有三处（字段必填性、地址数量上限、校验时机）三个开发者**恰好趋同**——但均靠"对齐主流电商"的行业惯例填坑，而非需求本身提供信息。趋同不等于无缺口：换个没有电商背景的开发者，必填性、上限都可能不同。

> 验证方法：3 个独立 AI 开发者（不同技术栈与产品背景人设、互不知晓、仅获需求原文）各自产出实现决策清单，对比决策差异。分歧显著 = 信息缺口实证存在。

## 应补充的内容

1. 目标平台与形态：Web 后台 / H5 / 小程序，表单承载形式（弹窗 / 抽屉 / 独立页）；
2. 字段级校验表：每字段的必填性、类型、长度上下限、字符集限制（是否禁 Emoji）、格式正则；
3. 手机号口径：是否仅限大陆手机号、+86 前缀与座机的处理策略（拒绝 / 归一化）；
4. 省市区实现方式：级联选择器 + 数据源与存储格式（行政区划码 / 名称快照）；
5. 地址数量上限及达到上限后的交互；
6. 保存失败时的表单状态（数据保留策略）与错误提示方式；
7. 验收标准：给出合法 / 非法输入示例清单。
