# R-S31-P1 回调通知未定义投递语义与安全契约

- **场景**：S31 消息推送/回调　**标签**：[P1-不完整](../../知识库/无效需求标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，6 组冲突性假设：失败重试/安全验证/内容格式/重复乱序/地址管理/长期不可用）

## 命中条件

**正向特征（须出现）**：

- **F1 回调/推送意图声明**："xx 后/事件发生时 + 通过/以 + Webhook/回调/消息推送/异步通知 + 通知/告知 + 接收方"类结构。
  - 例："**支付成功后通过 Webhook 通知**业务系统" → F1 成立；"状态变更时**回调**合作方接口" → F1 成立。
- **F2 投递语义缺席**：失败怎么办（重试/放弃）、怎么防伪造（签名/验证）、内容含什么（全量/摘要/信号）**全部缺席**。

**反向特征（须全部不出现）**——出现任何一个即不命中：

- **B1 失败重试定义**：失败后的重试策略与兜底（退避重试 N 次 / 死信告警 / 对账兜底）。
  - 例："失败后**指数退避重试 5 次**，仍失败告警人工处理" → B1 出现。
- **B2 安全契约**：签名 / 验证 / 防重放的约定。
  - 例："通知带 **HMAC 签名**，接收方须验签" → B2 出现。
- **B3 内容与幂等约定**：消息体格式（全量字段/摘要）与重复投递的处理约定。
  - 例："消息含**全量字段+event_id**，接收方按 event_id **幂等**" → B3 出现。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S31-P1
```

判定式读法：**左边**（发了通知，就一句）**同时右边**（失败重试、安全验证、内容幂等一个没说）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "支付成功后通过 Webhook 通知业务系统。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "支付成功后通过 Webhook 通知" |
| F2 | ✓ | 投递语义全缺席 |
| B1 | ✗ | 失败重试无 |
| B2 | ✗ | 签名验证无 |
| B3 | ✗ | 内容/幂等无 |

→ **命中**：实证显示 6 组互斥——失败重试（指数退避 10 次+死信告警 vs 固定 3 次放弃等对账 vs 不重试仅打日志——接收方宕机 1 小时，A 的通知必达可查，B/C 直接丢失）、安全验证（强制 HMAC 签名+防重放 vs 仅 HTTPS vs 无验证——攻击者可向 B/C 的回调端点**伪造"支付成功"通知实现未付款发货**）、内容格式（结构化事件+全量字段 vs 摘要 JSON vs 极简信号——接收方凭通知一次入账 vs 必须二次回查，集成工作量互斥）、重复/乱序（at-least-once+event_id 幂等 vs 假定 exactly-once 覆盖更新 vs 不处理反查为准——上游补发同一事件，B 的非幂等消费方（加余额）重复执行造成资损）、地址管理（控制台自助配置 vs 配置文件 vs 硬编码——换地址 A 自助即时生效，B/C 须发版产生中断窗口）、长期不可用（死信+补偿查询 API vs T+1 对账人工修复 vs 丢弃靠轮询兜底）。

**例 2（不命中）**：

> "支付成功后 Webhook 通知业务系统：带 HMAC 签名；失败指数退避重试 5 次后告警；消息含 event_id 全量字段，接收方幂等消费。"

B1、B2、B3 全部出现 → **不命中**。

## 说明

本规则检测回调/推送类需求的**投递契约缺失**，与事件类型无关（支付/订单状态/库存变更回调均适用）。缺口实质：异步通知契约 = 可靠性（重试+兜底）× 安全性（签名防伪）× 消费契约（格式+幂等）。异步通知与同步调用的本质区别：**发出去不等于收到了，收到了不等于对了**——网络会丢（需要重试策略）、端点会被攻击（需要验签防伪造）、上游会补发（需要幂等）。三个缺口可以叠加成复合事故：无验签（可伪造）+ 假定 exactly-once（无幂等）= 攻击者伪造通知重复入账的资损链路——实证中 B+C 组合正是此路径。异步契约还是**双方协议**：发送方的选择直接决定接收方的实现义务（验签、幂等），一方未定义则另一方无从配合——集成联调时才发现契约真空，是回调类需求最常见的返工原因。

## 误报注意

1. **遵循平台规范**："回调遵循微信/Stripe 式标准 Webhook 规范（含验签重试）"——B1–B3 由外部规范承载，不命中，需确认双方都按规范实现；
2. **内网可信环境**："仅内网系统间通知，网关已管控来源"——B2 由网络层承载，不命中（但重试与幂等仍需核对）；
3. **通知仅为提示无资金语义**：纯提醒类通知（"有人@你"）——伪造与丢失后果轻微，降级为提示。

## 漏报注意

1. **重试有值无兜底**："失败重试 3 次"出现 B1 但重试耗尽后怎么办未说——部分定义变体，按要素核对；
2. **安全词弱出现**："加个 token"——静态 token 与签名防重放强度不同，B2 需按实际强度判定；
3. **MQ 与 Webhook 混述**：消息走 MQ 而非 HTTP 回调时，可靠性语义由 MQ 承载（ack/重投），规则应只检 MQ 未覆盖的要素（消费幂等/顺序）——载体不同，要素清单相应调整。
