# R-S20-P1 二次确认未定义覆盖范围与确认语义

- **场景**：S20 确认/二次确认　**标签**：[P1-不完整](../../知识库/缺陷标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，5 组冲突性假设：覆盖范围/确认形式/可撤销性/弹窗信息量/确认层级记忆）

## 命中条件

**正向特征（须出现）**：

- **F1 确认要求声明**："xx 操作 + 需要/要/必须 + 二次确认/确认弹窗/确认一下"类结构，或"删除/危险操作要弹窗确认"。
  - 例："**删除操作需要二次确认**" → F1 成立。
- **F2 规则一句话止**：需求止于确认要求本身，覆盖范围、确认形式、确认后可撤销性**全部缺席**。

**反向特征（须全部不出现）**：

- **B1 覆盖范围限定**：哪些操作触发确认的界定（"仅批量删除"/"所有高危操作含注销"）。
  - 例："**仅批量删除**需二次确认，单条直接删" → B1 出现。
- **B2 确认形式定义**：弹窗一键 / 输入实体名强确认 / ActionSheet 的指明。
  - 例："需**输入项目名称**才能执行删除" → B2 出现。
- **B3 确认后行为**：确认执行后的可撤销性说明（撤销窗口/回收站/不可逆警示）。
  - 例："确认后**仍可从回收站恢复，保留 30 天**" → B3 出现。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S20-P1
```

判定式读法：**左边**（要求二次确认，就一句话）**同时右边**（覆盖范围、确认形式、确认后行为全没定义）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "删除操作需要二次确认。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "删除操作需要二次确认" |
| F2 | ✓ | 全文一句，三要素全缺席 |
| B1 | ✗ | 哪些删除触发确认无 |
| B2 | ✗ | 什么形式的确认无 |
| B3 | ✗ | 确认后可否撤销无 |

→ **命中**：实证显示 5 组互斥——覆盖范围（仅批量/高危 vs 所有删除+全部高危操作 vs 恰好所有删除按钮）、确认形式（轻量一键 vs 输入实体名强确认 vs 原生 confirm）、可撤销性（5 秒撤销+30 天回收站 vs 确认即不可逆 vs 确认即物理删除，误删后能否自救三案对立）、弹窗信息量（仅数量 vs 级联影响明细+不可恢复警示 vs 固定一句）、层级记忆（会话内可跳过 vs 每次必确认）。

**例 2（不命中）**：

> "批量删除需二次确认：弹窗展示将删除的数量与级联影响，输入'删除'二字确认；删除后数据进入回收站保留 30 天。"

B1（批量删除）、B2（输入文字强确认）、B3（回收站 30 天）全部出现 → **不命中**。

## 说明

本规则检测确认类需求的**确认语义缺失**，与操作类型无关（删除/注销/提交/支付确认均适用）。缺口实质：二次确认需求 = 覆盖范围 × 确认强度 × 确认后语义。"需要二次确认"只是意图声明——覆盖范围决定用户在哪被拦（单条删免确认直接删 vs 强确认，误操作保护面截然不同）；确认强度决定操作成本（一键 vs 输入名称，相差一个数量级）；确认后语义决定误删后果（撤销窗口可自救 vs 确认即终点）。三者的组合是产品风险偏好的表达，无业务常识可依，纯决策空间——且相互补偿（轻确认+可撤销 ≈ 强确认+不可逆的保护效果），缺失任一维都让另外两维的意图无从判断。实证中最重的一组：可撤销性二对一对立，误删后"能自救"与"数据即刻消失"直接相反。

## 误报注意

1. **平台确认规范引用**："确认交互遵循设计系统规范"——B1–B3 以平台规范形式存在，需人工确认规范真实定义了范围/强度/撤销语义；
2. **合规强制的固定形式**："按监管要求，注销需输入手机号验证码确认"——形式与范围由外部规定承载，不命中（但确认后语义仍需核对）；
3. **确认仅为提交前置**："表单提交前确认信息"——上下文已含确认内容（表单本身），范围无歧义时降级为提示。

## 漏报注意

1. **部分定义**："删除要弹确认框"出现 B2 弱形式（弹框）但范围/可撤销性未说——部分定义变体，需逐要素核对；
2. **确认与操作分离表述**："危险操作要有保护"——"保护"是确认、防抖还是撤销的上位词，F1 需语义级识别确认意图；
3. **覆盖范围口语化**："删东西前问一句"——B1/B2 以口语弱形式出现，词表需覆盖"问一句/拦一下/提示下"类表述。
