# R-S01-P4 以"与现有系统一致"隐藏假设

- **场景**：S01 表单（新增/编辑），但规则适用于任何出现"与现有一致"表述的功能需求　**标签**：[P4-隐含假设](../../knowledge/缺陷标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，分歧：'现有系统'被解读为 App 交互规范/接口规范/数据建模规范三种互斥含义；附带物理 vs 逻辑删除等根本对立）

## 命中条件

**正向特征（须出现）**：

- **F1 参照物引用**：出现"与/和/跟 + 现有系统 / 现有功能 / 现有逻辑 / 现有系统保持一致 / 老系统 / 原系统 / 之前的版本"类外部参照表述。
  - 例："删除操作**和现有系统保持一致**" → F1 成立；"交互**跟老系统一样**" → F1 成立。
- **F2 一致性未指明对象**：参照物存在，但**未说明一致的到底是哪个维度**（交互 / 接口 / 数据行为 / 视觉 / 权限）。
  - 例："和现有系统保持一致"（一致什么？没说）→ F2 成立；"交互和现有系统一致，但数据要软删"（指明了维度且有例外）→ F2 不成立。

**反向特征（须全部不出现）**：

- **B1 参照锚点**：系统名 / 版本号 / 页面名 / 功能名 / 需求编号 等可定位的参照物。
  - 例："与**订单中心 v2.3** 的地址删除一致" → B1 出现，不命中（但仍需人工核对锚点有效性）。
- **B2 维度说明**：交互 / 接口 / 数据行为 / 视觉样式 / 权限模型 等指明"一致"维度的词。
  - 例："交互**和现有系统一致**（指交互维度）" → B2 出现，不命中。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 → 命中 R-S01-P4
```

判定式读法：**左边**（引用了参照物，但没说一致的维度）**同时右边**（参照物不可定位、维度未指明）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "地址删除功能：用户在地址列表页可以删除不需要的地址，删除后地址不展示。删除操作和现有系统保持一致。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "和现有系统保持一致" |
| F2 | ✓ | 一致的维度（交互？接口？数据？）未指明 |
| B1 | ✗ | "现有系统"无名称/版本，不可定位 |
| B2 | ✗ | 无维度词 |

→ **命中**：参照物模糊 + 维度未指明，开发各自解读（实证：三人分别理解为 App 交互规范、RESTful 接口规范、数据建模规范）。

**例 2（不命中）**：

> "删除交互与现有 App 地址簿 v2.0 的左滑删除一致，但数据保留 30 天可恢复。"

B1（App 地址簿 v2.0）、B2（交互）出现，且有显式例外说明 → **不命中**。

## 说明

本规则检测**外部参照的不可解析性**，与参照的具体内容无关。缺口实质："与 X 一致"把决策外包给了一个未定义的参照物——每个开发者按自己最熟悉的层（交互层/接口层/数据层）去解读，产出在"删了能不能恢复"这类根本行为上对立（实证分歧含物理删除 vs 软删 180 天）。有效的一致性引用须同时具备：可定位的锚点（系统名/版本/页面）+ 指明的维度 + 显式例外。

## 误报注意

1. **团队共识参照**：小团队口头共识里"跟现有的一致"可能确实人人皆知所指——规则无法感知团队上下文，命中后由人确认是否豁免；
2. **同文档内引用**："与本文档 3.2 节的删除逻辑一致"——参照在同文档可解析，不命中；
3. **行业惯例引用**："与主流电商平台一致"属于设计原则表述而非具体行为引用，交由人工判断。

## 漏报注意

1. **隐性参照**：不出现"现有系统"字样，但通篇使用未定义的内部术语（"按老流程走""和上次那个一样"）——F1 的词表需扩展覆盖口语化参照；
2. **锚点存在但失效**：给出了系统名/版本但该版本已下线或行为已变更——B1 打破命中但缺口实际存在，属人工核对范畴；
3. **多参照冲突**：同时引用两个参照物且行为不一致——F2 判定应升级为"存在未消解的参照冲突"。
