# R-S41-P2 验收标准用"正常/可用"替代完成定义

- **场景**：S41 验收/成功标准　**标签**：[P2-不可验证](../../知识库/无效需求标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，8 组冲突性假设：正常口径/测试深度/性能门槛/安全门槛/数据校验/监控回滚/验收主体/缺陷阻断）

## 命中条件

**正向特征（须出现）**：

- **F1 完成标准声明**："做完/完成后 + 要能/达到/可以 + 正常使用/可用/上线/交付/生产可用"类结构。
  - 例："功能做完后**要能正常使用**，**达到可上线的程度**" → F1 成立。
- **F2 完成定义缺席**：什么是"正常"、什么是"可上线"——测试口径、门槛清单（性能/安全/数据/监控）、验收主体、缺陷阻断策略**全部缺席**，"做完"无客观判据。

**反向特征（须全部不出现）**——出现任何一个即不命中：

- **B1 判定口径**：正常/完成的可测定义（"全功能无 P2 级以上缺陷"/"主流程用例 100% 通过"）。
  - 例："验收以**测试用例全量通过、无 P2 以上缺陷**为准" → B1 出现。
- **B2 门槛清单**：上线的具体门槛（性能指标/安全扫描/数据比对/监控就位，至少一项明确）。
  - 例："压测 **QPS ≥500**，安全扫描无高危" → B2 出现。
- **B3 验收主体**：谁验收谁签字的指明（产品/测试/客户/开发者自评）。
  - 例："**产品和测试双签字**后方可上线" → B3 出现。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S41-P2
```

判定式读法：**左边**（给了完成标准，但标准是"正常""可上线"这类空词）**同时右边**（判定口径、门槛清单、验收主体一个没出现）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "功能做完后要能正常使用，达到可上线的程度。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "要能正常使用，达到可上线" |
| F2 | ✓ | 完成定义全缺席 |
| B1 | ✗ | 无判定口径 |
| B2 | ✗ | 无门槛清单 |
| B3 | ✗ | 无验收主体 |

→ **命中**：实证显示 8 组互斥——"正常使用"口径（全功能含边界异常无缺陷 vs 主流程能走通 vs 自己点一遍不报错——边缘功能在 B/C 交付物上直接报错）、测试深度（自动化全量+覆盖率门禁 vs 手工全量+演示冒烟 vs 仅自测——回归缺陷在 C 要用户踩到才暴露）、性能门槛（压测达标硬门槛 vs 演示不卡 vs 无要求——高峰期 C 崩溃 A 稳定）、安全门槛（扫描通过才可上 vs 推到后续 vs 不评估——B/C 可能带注入漏洞上线）、数据校验（全量比对一致 vs 主流程抽验 vs 肉眼——订单算错在 C 直达用户）、监控回滚（告警就位+回滚演练 vs 口头约定 vs 热修——故障发现与恢复时长差数量级）、验收主体（测试+产品双签字 vs 老板演示拍板 vs 开发自评——C 无独立把关，理解偏差直达全部用户）、缺陷阻断（P2+ 全阻断 vs 仅主流程阻断 vs 带伤上线——已知缺陷暴露面完全不同）。

**例 2（不命中）**：

> "完成标准：主流程测试用例 100% 通过、无 P2 级以上缺陷；压测 QPS≥500；产品与测试双签字后上线，已知次要缺陷记录跟踪。"

B1、B2、B3 全部出现 → **不命中**。

## 说明

本规则检测验收标准的**空词替代完成定义**缺陷，与交付形态无关（功能上线/项目验收/外包交付均适用）。缺口实质：验收标准的价值在于**把"做完"从主观判断变成客观判据**；"正常使用""可上线"是验收想达到的状态而非判据——它们预设了"正常"有公共定义，但质量工程派（全功能无缺陷+门禁全过）、业务交付派（主流程通+演示不翻车）、极简派（自测无报错）对"正常"的三种解读跨度极大，且每一处差异都直接落在用户可感知的交付质量上。P2 的破坏机制在此完全显形：验收标准不可验证时，**判定权自动转移到实现者自我评价**——自评者天然宽松，"做完"的时刻被提前，未验证的缺陷面全部转嫁给用户。与 P3 的分界：P3 是形容词无量化（"要快"），P2 是**完成定义整体缺席**（何为做完、谁来判、什么拦得住）——前者缺标尺，后者连判据的框架都没有。S41 是 P2 的根因案例，S36（可靠性）与 S11（报表口径）是它在具体维度的投影。

## 误报注意

1. **组织级 DoD 承载**："完成定义遵循团队 DoD（含测试/评审/文档门禁）"——B1–B3 由组织定义承载，不命中，需确认 DoD 覆盖本项目特殊门槛；
2. **测试计划外部承载**："验收标准见测试方案"——B1/B2 以外部文档存在，不命中，需人工确认方案含验收主体与阻断规则；
3. **合同验收条款**：外包项目"验收按合同附件验收单执行"——B1–B3 由商务文档承载，不命中。

## 漏报注意：

1. **口径有主体无门槛**："产品验收通过即可"——B3 出现但性能/安全/数据门槛（B2）仍开放，部分定义变体，按要素核对；
2. **门槛单点出现**："性能要达标"——B2 弱出现但"达标"本身又是空词，需核实有无数值锚点，无锚点不构成 B2；
3. **"上线"语境偷换**："能上线"在内部工具语境可能实指"能部署给同事试用"——语境重定义时判定门槛相应降低，需结合上下文识别实际交付形态。
