# R-S21-P3 加载状态无形态定义不可验收

- **场景**：S21 加载/进度　**标签**：[P3-主观模糊](../../知识库/缺陷标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，2 组冲突性假设：加载形态/覆盖范围；延迟展示、超时兜底、阻断策略三方趋同剔除）

## 命中条件

**正向特征（须出现）**：

- **F1 加载要求声明**："加载/刷新/请求 + 要有/需要/展示 + 加载状态/加载效果/loading"类结构。
  - 例："页面加载**要有加载状态**" → F1 成立；"列表刷新时**要有加载效果**" → F1 成立。
- **F2 主诉词无形态**："加载状态/加载效果"作为整体泛指词出现，**无具体形态指定**（骨架屏/spinner/进度条/遮罩均未指明），也无覆盖范围界定（首次进入/局部刷新/所有请求）。

**反向特征（须全部不出现）**：

- **B1 形态指定**：骨架屏 / 转圈 / spinner / 进度条 / 遮罩 / 骨架 / loading 图标任一具体形态词。
  - 例："列表用**骨架屏**占位" → B1 出现。
- **B2 覆盖范围界定**：哪些场景出现加载态的说明（"仅首次进入 / 所有接口请求 / 局部刷新区域"）。
  - 例："**所有接口请求**都要有加载态" → B2 出现。
- **B3 量化或兜底约定**：超时时间、延迟展示阈值、"超时提示重试"类约定。
  - 例："**10 秒超时**转为可重试错误页" → B3 出现。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S21-P3
```

判定式读法：**左边**（要求有加载状态，但状态是什么形态没说）**同时右边**（形态、范围、量化兜底一个没出现）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "页面加载要有加载状态。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "要有加载状态" |
| F2 | ✓ | "加载状态"泛指，形态未指 |
| B1 | ✗ | 无骨架屏/spinner 等形态词 |
| B2 | ✗ | 覆盖范围未界定 |
| B3 | ✗ | 无超时/阈值约定 |

→ **命中**：实证显示 2 组三向互斥——形态（整页骨架屏灰块 vs 全屏居中转圈遮罩 vs 顶部细进度条，用户第一眼看到三种完全不同的东西）、覆盖范围（首次+路由切换 vs 所有请求含局部 vs 仅浏览器首次进入，点击搜索后分别看到局部灰块/全屏遮罩/毫无反应）。另三维度（延迟展示、超时兜底、阻断策略）三方趋同或 2:1 收敛，剔除为自由度。

**例 2（不命中）**：

> "列表首次加载用骨架屏占位，局部刷新在表格区域转圈；10 秒未返回提示超时可重试。"

B1（骨架屏+转圈）、B2（首次加载/局部刷新分工）、B3（10 秒超时）出现 → **不命中**。

## 说明

本规则检测加载类需求的**形态不可验收性**，与页面类型无关（列表/详情/大屏加载均适用）。缺口实质："要有加载状态"是体验意图声明而非规格——加载态的两大决策（什么形态、覆盖哪些场景）完全开放，三种实现给出三种用户第一印象，且都无法被判"不符合需求"（原文没有可对照的验收标准），这正是 P3 的核心特征：主观泛指词使需求**不可验证**。与 P1 的分界：本规则的缺口词是泛指主诉词（"加载状态"），不是决策点缺席——写需求者已意识到要加载态，但用了一个无形态的词把它带过。实测中该场景的默认值收敛度高于流程类（超时兜底、延迟策略三方趋同），冲突集中在形态与范围两维，恰是主诉词直接对应的维度。

## 误报注意

1. **设计规范兜底**："加载态按设计系统组件规范执行"——B1/B2 以规范形式存在，需人工确认规范覆盖本页面类型；
2. **技术框架默认**：上下文已指明用某组件库且其加载行为确定（如特定表格组件自带 loading）——形态由组件默认承载，不命中；
3. **原型图/视觉稿引用**："加载效果见交互稿"——形态在外部载体，需人工确认稿件真实包含加载态设计。

## 漏报注意

1. **形态词弱出现**："转一下""loading 一下"——B1 以口语弱形式出现（都指向 spinner），需识别后判定是否足以收敛形态；
2. **范围半界定**："列表要有加载状态"——载体（列表）出现但首次/局部分工未说，B2 部分出现，属部分定义变体；
3. **进度细分场景**：上传/下载进度的"进度条"需求形态已含在主诉词内（进度即形态），不适用本规则的泛指判定，走 S04/S21 其他规则。
