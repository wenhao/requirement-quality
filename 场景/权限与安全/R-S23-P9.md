# R-S23-P9 权限管理未圈定管控对象与粒度

- **场景**：S23 角色与权限　**标签**：[P9-范围失焦](../../知识库/无效需求标签.md)
- **验证**：多解实现验证通过（2026-10-20，N=3，5 组冲突性假设：权限模型/管控层级/管理主体/数据范围与组织/变更审计）

## 命中条件

**正向特征（须出现）**：

- **F1 权限意图声明**："支持/需要/要有 + 权限管理/权限控制/权限体系/角色权限"类结构。
  - 例："系统**需要支持权限管理**" → F1 成立；"**支持角色权限**" → F1 成立。
- **F2 管控对象裸奔**："权限"管什么（页面/按钮/接口/数据哪些层）、粒度多细、谁有权分配**全部缺席**，无任何限定性说明。

**反向特征（须全部不出现）**——出现任何一个即不命中：

- **B1 管控层级界定**：管到哪一层的说明（"菜单+按钮级"/"页面级"/"数据范围"）。
  - 例："权限**到按钮级**（页面可见但删除按钮可单独禁用）" → B1 出现。
- **B2 管理主体说明**：谁能配权限（超管专属/租户自治/可下放部门管理员）。
  - 例："**仅超级管理员**可配置角色" → B2 出现。
- **B3 角色/模型定义**：角色体系或模型形态的定义（预置哪些角色/RBAC 矩阵/与组织架构的关系）。
  - 例："**预置管理员/操作员/只读三角色**，可自定义扩展" → B3 出现。

### 判定

```
(F1 ∧ F2) ∧ ¬B1 ∧ ¬B2 ∧ ¬B3 → 命中 R-S23-P9
```

判定式读法：**左边**（声明要权限管理，但管什么、多细、谁配全没说）**同时右边**（层级、主体、角色定义一个没出现）→ 命中。

### 判定过程示例

**例 1（命中）**：

> "系统需要支持权限管理。"

| 特征 | 结果 | 依据 |
|---|---|---|
| F1 | ✓ | "需要支持权限管理" |
| F2 | ✓ | 管什么全没说 |
| B1 | ✗ | 无层级界定 |
| B2 | ✗ | 无管理主体 |
| B3 | ✗ | 无角色定义 |

→ **命中**：实证显示 5 组互斥——权限模型（可配置 RBAC 矩阵 vs 订阅档位×功能开关 vs 硬编码两档，客户能否自助新增"财务专员"角色三案不同）、管控层级（页面+按钮+接口+数据四层 vs 模块+页面两层 vs 仅接口+菜单显隐）、管理主体（管理界面可下放 vs 平台管套餐+租户管成员双层 vs 无界面改库指定）、数据范围（按部门树隔离 vs 租户内共享 vs 全局共享——普通销售在 A 只看自己的客户，B/C 看到全部）、审计（全量权限变更+操作审计 vs 仅订阅事件 vs 无审计）。

**例 2（不命中）**：

> "权限管理：预置管理员/操作员/只读三角色可自定义；管到按钮级；仅超级管理员可配置，配置变更全量审计。"

B1、B2、B3 全部出现 → **不命中**。

## 说明

本规则检测权限类需求的**管控范围失焦**，与系统类型无关（CRM/ERP/SaaS 后台均适用）。缺口实质：权限需求 = 管什么（层级）× 多细（粒度）× 谁配（管理主体）× 与组织的关系（数据范围）。"支持权限管理"与 S19 的"通知用户"同构——把最重的决策名词留成泛指：三层实现分别收敛为 RBAC 平台、订阅功能开关、固定两档三种互斥产品，验收时"权限管理"四个字无法裁决任何一方不合格。权限是横向切面需求（每个功能都要过一遍），范围失焦的代价被所有功能放大。

## 误报注意

1. **框架级权限惯例**：上下文已指明用某权限体系（"基于 XX 平台的 RBAC"）——B1–B3 由平台承载，不命中，需人工确认平台粒度满足业务；
2. **上下文已有角色清单**：前文已定义角色体系（"角色分为 A/B/C…"）而本条仅引用——B3 以引用形式存在，跨段落核对；
3. **明确的全开放声明**："所有人都能用所有功能，只区分管理员"是显式极简决策——范围已圈定（两档），不命中本规则。

## 漏报注意

1. **部分界定**："支持角色权限，可以配菜单"——B1 弱出现（菜单级）但按钮/数据/管理主体仍开放，部分定义变体，逐要素核对；
2. **权限藏在功能需求里**："订单模块只有主管能审批"——单点权限规则出现时不适用本规则（那已圈定对象），但若全篇仅此一句而无体系性说明，体系缺口仍在，需语义级识别；
3. **口语化**："得有个权限，不是谁都能进"——F1 词表需覆盖口语权限意图。
